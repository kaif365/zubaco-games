--------------------------------------------------------------------------------
1. OBJECTIVE
--------------------------------------------------------------------------------
Collapse the two remaining "split-brain" runtime planes onto a single
authoritative implementation each, WITHOUT changing business rules or
transaction semantics and WITHOUT breaking the build:

  PART A (Money)       Route live wallet mutations through WalletLedgerService
                       instead of bespoke direct $transaction blocks, wherever
                       it is genuinely safe to do so.
  PART B (Enforcement) Make EnforcementService the only authoritative path that
                       writes User.is_banned; protect enforcement endpoints and
                       remove spoofable identity fields.

The deliverable is honesty about what is now truly single-plane at RUNTIME and
what still remains split.

--------------------------------------------------------------------------------
2. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------
Money plane:
  - The two CLEANLY-routable live money flows were moved onto the ledger:
      * Referral bonus  -> WalletLedgerService.post(REFERRAL_CREDIT)
      * Season entry fee -> WalletLedgerService.debitEntryFee(...)
    Tournament prize was already routed in ROLLOUT-003 (TOURNAMENT_PAYOUT).
  - Storage-level idempotency was added (Transaction.ledger_key UNIQUE) so the
    ledger no longer relies on Redis locks alone.
  - Deposit and withdrawal/settlement were deliberately NOT routed (see s.7/s.12)
    because doing so would change transaction semantics (double-credit / loss of
    the PENDING lifecycle). They remain on WalletService and are documented.
  => Money plane is MORE unified but NOT 100% single-plane. PARTIALLY RESOLVED.

Enforcement plane:
  - Every authoritative-eligible User.is_banned write in the canonical source now
    flows through EnforcementService.enforce(): the anti-cheat auto-ban, the
    admin flag-review ban, and the admin banUser endpoint. AntiCheatService no
    longer writes is_banned directly for bans.
  - The only remaining direct is_banned write is unbanUser, because
    EnforcementService has no authoritative "un-enforce" / reversal action
    (inventing one is a redesign and out of scope). It is service-identity gated.
  - The spoofable body.admin_id was removed from the review/ban endpoints; the
    actor is now derived from the authenticated service identity.
  => Enforcement bans are single-plane; unban remains direct. PARTIALLY RESOLVED.

Build is GREEN (prisma generate + nest build, exit 0).

--------------------------------------------------------------------------------
7. RUNTIME MONEY FLOW (AFTER)
--------------------------------------------------------------------------------
  Deposit  : UNCHANGED -> creditDepositAtomically.   [ledger-bypass, INTENTIONAL]
             Reason: the live deposit uses a pre-created-PENDING-row claim model.
             ledger.post() creates a fresh COMPLETED row, so routing it would
             DOUBLE-CREDIT (one claimed row + one new ledger row). Genuinely not
             safe without rewriting the gateway lifecycle = transaction-semantics
             change. Left as-is. (DEPOSIT_CREDIT operation deliberately NOT added.)
  Entry fee: tournament.register -> WalletService.deductEntryFee
             -> WalletLedgerService.debitEntryFee(ENTRY_FEE_DEBIT).               [ledger]
             Same bonus-first split, same single ENTRY_FEE row, same combined
             balance_after, same "Insufficient balance for entry fee" error.
             NOW idempotent per (season,user) via ledger_key + audited.
  Referral : social.service x2 -> WalletService.creditReferralBonus
             -> WalletLedgerService.post(REFERRAL_CREDIT, bucket='bonus').         [ledger]
             Same REFERRAL_BONUS type + bonus bucket. NOW idempotent per
             (referral,user) so referrer and referred each credit exactly once.
  Prize    : UNCHANGED -> ledger.post(TOURNAMENT_PAYOUT).                          [ledger]
  Withdraw : UNCHANGED -> requestWithdrawal.          [ledger-bypass, INTENTIONAL]
             Reason: ledger.post() force-writes status='COMPLETED'; withdrawals
             require a PENDING row until external RazorpayX disbursement, then a
             settlePending() transition. Routing through post() would skip the
             PENDING lifecycle = transaction-semantics change. Left as-is.
  Admin adj: UNCHANGED -> ledger.post(...).                                        [ledger]

  Net: 3 of 5 live money flows (entry-fee, referral, prize) + admin adjustments
  now execute on the authoritative ledger. Deposit + withdrawal still bypass it.
