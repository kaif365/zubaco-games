6. WALLET INTEGRATION
--------------------------------------------------------------------------------
Backend verified: WalletController + WalletService + KycService.
  - Balance / bonus / KYC: useQuery(['wallet']) -> GET /wallet returns the Wallet
    row { balance, bonus_balance, kyc_verified, currency, ... }. balance and
    bonus_balance are Prisma Decimals (JSON strings) and are Number()-coerced.
    KYC status is read from the authoritative wallet.kyc_verified (no hardcode);
    the KYC banner and the Withdraw button's disabled state are driven by it.
  - Transactions: useQuery(['wallet','transactions']) -> GET /wallet/transactions
    returns { transactions, total, page, totalPages }. Rendered with a
    type->label map, credit/debit direction derived from TransactionType, real
    amounts, and a relative "time ago" derived from created_at.
  - Pull-to-refresh (RefreshControl) refetches wallet + transactions.
  - Loading (ActivityIndicator), empty ("No transactions yet") and error states
    ("Could not load ...") are all handled.
  - WITHDRAW (two-step OTP flow, exactly as the backend requires):
      Step 1  POST /wallet/withdraw {amount}     -> { withdrawal_id, message } (OTP sent)
      Step 2  POST /wallet/withdraw/confirm {withdrawal_id, otp}
                                                  -> { new_balance, net_payout, tds_deducted, status }
      Implemented as a modal: amount entry -> "Send OTP" -> OTP entry -> "Confirm".
      On success the wallet cache is invalidated. Backend validation messages
      (min/max, daily limits, KYC required, insufficient balance) surface to the
      user via the thrown Error message (no client-side hardcoded limits).
  - DEPOSIT:
      POST /wallet/deposit/create-order {amount} -> { order_id, amount, currency, key_id }
      then POST /wallet/deposit/verify {order_id, payment_id, signature}.
      The full JS integration is wired: amount modal -> create order -> (Razorpay
      checkout) -> verify -> invalidate wallet. The native capture step uses the
      react-native-razorpay SDK, loaded via an optional lazy require so the app
      still compiles/runs when the native module is absent; when absent the
      server-side (idempotent) order is created and the user is told to complete
      payment. See section 19 for the one remaining dependency.

7. NOTIFICATIONS INTEGRATION
--------------------------------------------------------------------------------
Backend verified: NotificationController + NotificationService + Prisma
Notification model.
  - List: useQuery(['notifications']) -> GET /notifications returns
    { notifications, total, unread_count, page }. The Notification row has no
    icon/timeAgo, so the UI derives an icon from NotificationType (STAGE_OPEN,
    PRIZE_WON, FRIEND_REQUEST, CHALLENGE, SYSTEM, PROMOTION, ...) and a relative
    time from created_at.
  - Mark-as-read PERSISTS: useMutation -> POST /notifications/:id/read with an
    OPTIMISTIC cache update (onMutate flips read=true and decrements
    unread_count) and onSettled invalidation so the read state is reconciled with
    the backend and survives refetch/return. onError rolls back.
  - Real pull-to-refresh (RefreshControl -> refetch), loading and error/empty
    states. The setTimeout mock and local-only useState list were removed.

9. FREE PLAY INTEGRATION
--------------------------------------------------------------------------------
Backend verified: FreePlayController + FreePlayService + EnergyService.
  - Energy: useQuery(['energy']) -> GET /free-play/energy returns
    { current_lives, max_lives, bonus_lives, total_available, ... }. The badge
    shows total_available/max_lives (no hardcoded 5/5).
  - Progress: useQuery(['progress']) -> GET /free-play/progress returns a map
    keyed by GameType with { current_level, highest_level, best_score, ... }.
    Each card's "Best" is the real best_score; the level to start is the real
    current_level.
  - Start a REAL session: on tap, useMutation calls
    POST /free-play/start {game_type, level} -> { session_id, server_seed, config }
    (this consumes a life server-side) AND reads the user's access token from
    SecureStorage in parallel, then navigates to the Game route with:
        sessionId = session.session_id   (REAL backend session id)
        token     = user access token    (REAL auth token; NOT 'placeholder-token')
        gameUrl   = resolveGameUrl(game)  (real per-game URL, allowlist-compatible)
        gameType, level, mode='FREE_PLAY'
    energy is refetched afterwards. A "Starting session…" indicator is shown.
  - PLACEHOLDER_GAMES, hardcoded energy, `session-${gameId}` and
    'placeholder-token' were all removed.
  - Result submission: GameScreen, on GAME_COMPLETED with mode='FREE_PLAY',
    calls POST /free-play/submit {session_id, score, duration_ms} before
    navigating back (backward compatible — HomeScreen, which also uses the Game
    route, passes no mode and is unaffected).
