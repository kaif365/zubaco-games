6. G-01 SUMMARY — Sequence Recall WebSocket Authentication (P0)
--------------------------------------------------------------------------------
Backend (sequence-recall-backend/src/game/game.gateway.ts — the realtime
gameplay gateway registered in GameModule, namespace '/realtime'):

  BEFORE: The afterInit() Socket.IO middleware fabricated a fake identity for
          every connection:
              userId: randomUUID(), userName: 'Mock User',
              sessionId: randomUUID()
          ("Mocking user — in production these come from JWT verification").
          Any client could connect and play as an anonymous, unauthenticated
          user. This was a production authentication bypass.

  AFTER:  The middleware now performs real authentication, mirroring the game's
          own HTTP SessionGuard and the strongest existing gateways
          (Infinity-loop / Speed-Type-Answer):
            1. Extract the bearer token from handshake.auth.token or the
               Authorization header; reject (TOKEN_INVALID) when absent.
            2. verifyToken(token) — cryptographic JWT verification
               (throws TOKEN_EXPIRED / INVALID_TOKEN on failure).
            3. Enforce userType === USER_TYPES.USER and tokenType in
               { LOGIN, GAME_SESSION } (TOKEN_INVALID otherwise).
            4. UserService.verifyUser(sessionId, userId, token) — the
               authoritative session/user check (Redis session + user, with a
               user-microservice fallback). This rejects expired sessions and
               banned/removed users (the user service is the source of truth for
               ban status).
            5. Populate socket.data with the REAL user id, name and session id.
          Any failure rejects the connection (next(Error)); the socket never
          enters gameplay. UserService is provided by the @Global() UserModule,
          so no GameModule wiring change was needed.

  Removed: `randomUUID` import and all mock-identity logic.
  Preserved: all gameplay handlers (game:start / game:move / game:complete),
             the Restate session flow, room/socket semantics, and the SocketData
             shape.

  Note on the second gateway: sequence-recall-backend also contains
  src/ws/game.gateway.ts (a generic '/game' gateway in WsModule). It ALREADY
  verifies the JWT on connect and is byte-for-byte identical to the
  Speed-Type-Answer reference gateway, so it required no change.

Frontend (sequence-recall-frontend/src/services/httpClient.ts):

  BEFORE: On HTTP 401 the response interceptor silently called fetchDevSession()
          to mint a brand-new anonymous dev session and stored the token,
          masking real authentication failures (TODO(temp): 401 dev-session
          refresh).
  AFTER:  On 401 the client now clears local auth state, shows the
          session-expired toast, and redirects to '/'. No silent session
          recovery occurs. The temporary STORAGE_KEYS / fetchDevSession imports
          and the AUTH_RECOVERY_FLAG were removed.
  Scope note: A separate, broader dev-session bootstrap still exists in
          useAuthGate.ts and SequenceRecallGameShell.tsx (the dev auth entry
          flow). It is intentionally left untouched here to avoid an
          architectural change / API break, and is listed honestly in section 17.

7. G-02 SUMMARY — Pattern Survival Perfect-Round Hesitation Timing
--------------------------------------------------------------------------------
DTO (submit-game.dto.ts): added an OPTIONAL field
      roundTimings: z.array(z.array(z.number().int().min(0)).max(500)).max(500)
                     .optional()
   Optional => no API breaking change; existing clients keep working unchanged.

Service (game.service.ts, submitGame):
   A perfect round now requires zero mistakes AND human-like hesitation timing.
   After the server re-derives verifiedRounds and the capped verifiedPerfectRounds
   (= min(client perfectRounds, verifiedRounds)), if the client supplied
   roundTimings the timestamps for the verified rounds are run through the
   EXISTING engine/timingAnalyzer.ts analyzeInputTiming(). If the timing is
   flagged isSuspicious (e.g. inhuman, automated input cadence), the perfect bonus
   is voided (verifiedPerfectRounds = 0) and a cheat reason is recorded
   ("Perfect bonus rejected (timing): ...") through the existing cheat-flag flow.
   The inline parameter type of submitGame was widened with the optional
   roundTimings property to match the DTO.

   The pre-existing anti-cheat framework was reused as-is — no new anti-cheat
   subsystem and no architecture redesign. The TODO at the former line 91 is
   resolved.
