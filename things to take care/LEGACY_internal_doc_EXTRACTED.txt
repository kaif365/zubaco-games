02 · Project Understanding 
2.1 What Shunya Is 
Shunya is a mass-participation, skill-based elimination competition platform. Beginning with potentially 
millions of registered players, it applies a progressive filtration architecture across five distinct online 
stages — each testing a deeper cognitive dimension — before a physical finale determines a single 
champion.  
2.2 The Funnel Architecture 
The platform operates across three distinct phases: 
• 
Pre-Bucketing (Stages 1–3): Players are segmented by registration week into cohorts 
(Buckets). Each bucket independently completes three stages with ~50% elimination per stage. 
A cohort registering 1,000,000 players produces ~125,000 survivors. 
• 
Post-Bucketing (Stages 4–5): All surviving cohorts are merged into a unified competitive pool 
for two advanced stages testing persistence, strategic depth, and speed under pressure. 
• 
Offline Finale: The top few hundred survivors are invited to a physical venue for the final 
crowning event.

2.6 RNG Architecture - Server Seed + User Input Model 
Shunya's game fairness and anti-cheat integrity depend entirely on a deterministic, verifiable, 
server-authoritative random number generation system. The architecture below implements a 
dual-seed model: a server-generated secret seed (which the client never sees) combined with a user 
input hash (making each session uniquely tied to the user's actions). This design satisfies the NFR 
mandate for determinism while preventing pre-calculation attacks(This is according to the initial 
understanding and will inform you in advance if any changes are required).

04 · Proposed Solution Overview 
Shunya's gaming engine is not a monolithic game — it is a distributed game orchestration platform. 
Each of the games is a standalone microservice-WebApp with its own backend, communicating with a 
central Contests Service through defined OAuth and webhook contracts. This architecture ensures 
independence, scalability, and maintainability at every layer. 
4.1 Architecture Pillars 
Game WebApps (Frontend) 
All games are built as responsive WebApps rendered inside the host app's WebView. Each game is a 
self-contained unit with its own UI, game logic, and scoring logic. Games communicate with their own 
backends and with the Contests Service backend via defined events. 
Game Backends (Per-Game Microservices) 
Each game has a dedicated backend responsible for server-side state initialization (using deterministic 
seeds), validation of player submissions, score calculation, and event emission to the Contests Service. 
This ensures the client is never trusted for scoring. 
Contests Service Integration 
The Contests Service is the client's own backend. Our games integrate with it via: (1) OAuth-based 
session initialization at game start, and (2) Webhook-based score submission at game end. We will 
adhere strictly to the integration contract defined by the client's team. 
Adaptive MCQ Engine 
A shared, stateful MCQ engine serves question banks across Stages 1–5. The adaptive difficulty 
algorithm (2 consecutive correct → level up; 2 consecutive incorrect → level down) is implemented 
server-side and is deterministic per session seed. Question banks are rotated per cohort-session to 
prevent farming and Question banks need to be uploaded via Admin Panel with suggested format. 
Anti-Cheat Architecture 
Server-side validation for all solvable puzzles (mazes, Sudoku, sliding puzzles, Block Fill) with 
pre-calculated optimal solution sets. Session token invalidation on detection of abnormal input patterns 
(consistent responses across all events). Reaction time scoring implements a 0–5 second floor to 
eliminate pre-click exploits.

4.2.2 Infra + AWS: All Games + Core Infrastructure 
1. Automated Infrastructure (IaC & GitOps) 
● Terraform: We use Terraform to maintain four strictly isolated environments (Dev, QA, 
Staging, Prod). This ensures that infrastructure changes are tested before reaching production. 
● ArgoCD: By adopting a GitOps model, the EKS cluster state is automatically synchronized with 
our Git repository. This provides a version-controlled audit trail for all deployments. 
2. Scaling & Resilience 
● 100K CCU & Auto-Scaling: We are achieving this through EKS + Karpenter, which provides 
rapid, just-in-time node provisioning and "bin-packing" to handle traffic bursts more efficiently 
and cost-effectively than Fargate. 
● CDN & Image Optimization: We integrate CloudFront with an automated S3/Lambda@Edge 
pipeline for real-time WebP conversion and mobile-optimized delivery to ensure low latency 
and responsive gameplay. 
● Performance Profiling: Continuous monitoring is handled via Prometheus and Grafana to 
optimize CPU, GPU, and memory utilization, ensuring we meet strict NFR targets for smooth, 
deterministic performance. 
● Reliability & Security: We implement RDS Proxy to manage PostgreSQL connection spikes and 
AWS Secrets Manager for secure, version-controlled credential handling across all 13 
microservices 
3. Security & Containerization 
● Secrets Manager: All sensitive data, including database credentials and OAuth keys, are stored 
in AWS Secrets Manager and injected into pods via the CSI Driver to avoid plain-text 
environment variables. 
● Optimized Dockerization: We maintain 13 microservices using a standardized, multi-stage 
base image to reduce bloat and meet NFR targets for low CPU and memory utilization. 
4. Performance & Monitoring 
● Static Frontend: The game Webapp is served via S3 and CloudFront, utilizing WebP 
conversion and lazy-loading to minimize mobile latency. 
● Observability: Centralized Prometheus and Grafana dashboards provide real-time profiling of 
CPU, GPU, and memory usage.

5.2 Determinism & Consistency Implementation 
The NFR mandates that for a given seed, all game state and scoring must be identical. Our 
implementation approach: 
• 
All randomization (maze generation, puzzle scrambling, MCQ question selection, object 
placement) uses a seeded pseudo-random number generator (PRNG) — specifically 
seedrandom.js or an equivalent deterministic library. 
• 
Seeds are generated server-side at session initialization and stored in Redis. The seed is never 
exposed to the client directly. 
• 
Game state reconstruction (for validation) replays the PRNG with the same seed to verify 
submitted answers against the server-calculated expected state. 
• 
MCQ question sets are locked per cohort-session at the session initialization phase and served 
from a snapshot, preventing mid-session question bank updates from affecting ongoing games. 
5.3 Scalability Architecture 
Supporting 100K concurrent users and 10M+ MAU requires horizontal scaling at every layer: 
• 
Stateless Game WebApps served via CloudFront CDN — zero backend dependency for UI 
rendering 
• 
Game Backends deployed as auto-scaling ECS Fargate services behind an Application Load 
Balancer 
• 
Redis Cluster (ElastiCache) for session state — eliminates single-node bottlenecks 
• 
PostgreSQL with read replicas for score ledger reads; primary used only for writes 
• 
Asynchronous webhook delivery via SQS — decouples score submission from real-time game 
flow 
• 
Pre-warmed game instances during cohort competition windows to eliminate cold-start latency
