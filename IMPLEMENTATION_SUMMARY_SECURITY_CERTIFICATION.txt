SECTION 1 — EXECUTIVE SUMMARY
================================================================================
A complete zero-trust security review of the money-handling backend was
performed across authentication, authorization, input validation, financial
integrity, game integrity, web security, cryptography, dependencies,
configuration and DoS/resource exhaustion.

The backend is, on the whole, well-engineered from a security standpoint: the
financial ledger uses row-level pessimistic locking (SELECT ... FOR UPDATE) with
idempotency keys; all HMAC comparisons are constant-time; refresh tokens are
rotated and stored only as SHA-256 hashes; OTPs are bcrypt-hashed with layered
rate-limiting and brute-force lockout; service-to-service calls are HMAC-signed
with nonce replay protection and a clock-skew window; and there is NO use of
eval/child_process and NO string-concatenated SQL.

Seven findings were identified. Two were genuinely impactful and are now FIXED:
  * F1 (HIGH)  Rate limiting was completely INERT — ThrottlerModule and dozens
               of per-route @Throttle() decorators existed but no guard was
               bound, so zero 429s were ever produced. Fixed.
  * F2 (HIGH)  The real-money geo-fencing compliance guard read the wrong
               request property and therefore silently allowed EVERY
               authenticated user, including users in legally-banned states.
               Fixed.
Three were meaningful hardening gaps, now FIXED (F3 input-validation DTOs, F4 OTP
modulo bias, F5 payment-signature length guard). Two are documented as accepted /
recommended (F6 non-reachable transitive multer CVE; F7 OTP-gated phone linking).

Post-fix the entire 280-test matrix and the production build remain green.

Scope honesty: the repository is a monorepo. The audit and all hardening focused
on zubaco-platform (the real-money backend). The client repos
(zubaco-web-lobby, zubaco-admin-panel-repo, zubaco-mobile) and the game repos
received a surface-level review only and were NOT hardened in this pass — see
Sections 2 and 15.

SECTION 3 — AUTHENTICATION FINDINGS
================================================================================
Mechanisms: phone OTP (auto-register), Google ID-token, Apple identity-token,
JWT access (15m) + opaque refresh (7d), logout / logout-all.

VERIFIED SECURE (no issue — with reasons):
  * JWT access tokens: HS256 signed with JWT_ACCESS_SECRET; strategy sets
    ignoreExpiration:false; there is NO acceptance of alg=none (passport-jwt
    verifies with the configured secret). Secret is mandatory — config/index.ts
    throws at boot if JWT_ACCESS_SECRET / JWT_REFRESH_SECRET are unset.
  * Per-request ban enforcement: JwtStrategy.validate consults a short-TTL Redis
    ban cache with authoritative fallback to User.is_banned, so a banned user is
    rejected within seconds without waiting for token expiry. (CWE-613 mitigated.)
  * Refresh tokens: opaque uuidv4 (122 bits entropy), stored ONLY as SHA-256
    hash, with an expires_at check. Refresh performs ROTATION (old token deleted,
    new pair issued) and re-checks is_banned. Logout revokes the presented token;
    logout-all deletes all of a user's refresh tokens. (Token replay / session
    fixation mitigated — a stolen-then-rotated token becomes invalid.)
  * OAuth: Google/Apple ID tokens are verified SERVER-SIDE
    (googleStrategy.verifyToken / appleStrategy.verifyToken via jwks-rsa) before
    any account is created or logged in — forged identity is rejected.
  * OTP: bcrypt-hashed at rest; send limited to 5/hour/phone (Redis); verify has
    a global brute-force lockout (10 fails / 15 min) AND a per-record attempt cap
    (config.otp.maxAttempts=5); brute-force counter reset on success; OTP only
    logged in development, never in production.

FIXED:
  * F4 (LOW, CWE-331) OTP generation used `randomBytes % 10`, which is
    modulo-biased (256 is not a multiple of 10, so digits 0-5 were slightly more
    likely). Replaced with rejection sampling (reject bytes >= 250) so every
    accepted byte maps uniformly onto 0-9.

DOCUMENTED (not fixed this pass):
  * F7 (MEDIUM, CWE-287) /auth/link-account links a phone/Google/Apple identity
    to the caller's account WITHOUT proof of ownership (no OTP for phone, the
    provider_id is trusted for OAuth). Uniqueness is enforced (cannot steal an
    already-claimed identity), so the residual risk is pre-registration
    "squatting" of an unclaimed phone number, not takeover of an existing
    account. A proper fix requires an OTP re-verification sub-flow for phone
    linking and a verified-token requirement for OAuth linking — a login-flow
    change. Input validation for this route WAS hardened (F3). Recommended as the
    next auth change; left out of this pass to avoid an untested flow change.

SECTION 4 — AUTHORIZATION FINDINGS
================================================================================
VERIFIED SECURE:
  * User routes are protected by JwtAuthGuard; the authenticated userId is taken
    from the validated token (req.user.userId), never from the request body, so
    horizontal privilege escalation via body-supplied user id is not possible on
    the audited wallet/tournament/session endpoints.
  * Service-to-service surface (/admin/control-plane, /anti-cheat) is protected
    by ServiceIdentityGuard: per-service HMAC-SHA256 signature over a canonical
    (serviceId, method, url, timestamp, nonce, sha256(body)) string, a
    +/-60s clock-skew window, single-use nonces via Redis SETNX+EXPIRE (replay
    protection), constant-time signature comparison, key rotation (current+
    previous), and rejection of registry keys shorter than 32 chars.
  * Admin control-plane additionally enforces RBAC (AdminRole
    SUPER_ADMIN/FINANCE/READ_ONLY), idempotency and an audit trail.

FIXED:
  * F2 (HIGH, OWASP A01, CWE-863/CWE-639) GeoFencingGuard — which is applied to
    the paid-tournament registration and wallet deposit-order routes to block
    real-money play from Indian states where it is illegal — read
    `req.user?.id || req.user?.sub`. JwtStrategy.validate returns `{ userId }`,
    so that expression was ALWAYS undefined and the guard returned true for every
    authenticated user, i.e. the compliance control was silently disabled.
    Fixed to read `req.user?.userId` first (legacy keys kept as fallback). The
    guard now actually enforces the banned-state list.

NON-ISSUE (documented):
  * The legacy InternalApiGuard (static shared key) still exists in the tree but
    is NOT wired to any controller — ServiceIdentityGuard superseded it
    (AUTH-003). It is dead code, not an active weakness. Recommend deletion.

SECTION 5 — FINANCIAL SECURITY FINDINGS
================================================================================
The wallet/ledger core was audited as the highest-value attack surface.

VERIFIED SECURE (no issue — with reasons):
  * Concurrency / race conditions: every balance mutation happens inside a
    prisma.$transaction that first executes
    `SELECT * FROM "wallets" WHERE "user_id" = $1 FOR UPDATE` (pessimistic row
    lock) before computing the new balance. Concurrent credits/withdrawals on the
    same wallet serialize correctly — no lost-update / double-spend window.
  * Idempotency / duplicate payments: ledger operations short-circuit on an
    existing ledger_key ("duplicate: true"), and deposit settlement is claimed
    atomically (creditDepositAtomically) so the webhook path and the client
    verify path cannot both credit the same order (payment.captured is
    idempotent on repeated webhooks).
  * Withdrawals: debit the cash bucket immediately (funds reserved), require
    kyc_verified, reject on insufficient balance, record TDS as a separate
    COMPLETED row, and require an OTP confirmation step
    (/wallet/withdraw/confirm) — and the route is rate-limited (5/hour).
  * Deposit verification is defense-in-depth: HMAC signature check AND a
    re-fetch of the real Razorpay payment amount, rejecting on amount mismatch
    ("Payment amount mismatch") before crediting.
  * Amounts are class-validator bounded (deposit ₹10–₹1,00,000; withdrawal
    ₹100–₹50,000) and use Prisma.Decimal throughout (no float rounding on money).
  * Negative-amount / underflow guarded: `if (next.lessThan(0)) throw
    Insufficient balance`.

No CRITICAL or HIGH financial vulnerability was found. The financial layer is the
strongest part of the codebase.

SECTION 6 — GAME SECURITY FINDINGS
================================================================================
VERIFIED SECURE:
  * Scores submitted by the client are NOT trusted blindly: submissions pass
    through the verification pipeline (game-session/verification/*), and the
    session lifecycle is a strict state machine (session-lifecycle.ts) preventing
    out-of-order / replayed completions.
  * Tournament progression is an authoritative state machine
    (tournament-state.ts) with server-side reward payout (reward-payout.service)
    routed through the audited ledger; rewards are not client-controlled.
  * Anti-cheat flags + enforcement (ban) feed the JwtStrategy ban cache, so an
    enforcement decision takes effect on the next request.
  * SubmitTournamentResultDto bounds score (0–100000) and duration
    (1000–600000ms), rejecting absurd client values at the boundary.
  * RNG is deterministic/seeded (deterministic-rng.service) for reproducible,
    server-verifiable puzzles.

No score-tampering / fake-session bypass was found on the audited paths; client
trust is mediated by server-side verification and the ledger.

SECTION 7 — WEB SECURITY FINDINGS
================================================================================
VERIFIED / PRESENT:
  * helmet() sets standard security headers (X-Content-Type-Options, X-Frame-
    Options/frameguard for clickjacking, etc.). The API returns JSON only, so a
    strict document CSP is not the primary control here.
  * CORS is env-driven (CORS_ORIGINS) and defaults to an explicit localhost
    origin — NOT a reflected/wildcard origin — with credentials:true.
  * Body size capped at 1 MB (mitigates large-payload DoS).
  * Razorpay webhook has an IP-allowlist guard AND (primary control) HMAC
    signature verification — see Section 8.
  * No SSRF sink was found on user-controlled input; the only outbound HTTP is
    the webhook to a server-configured BASE_PLATFORM_WEBHOOK_URL.
  * No path/directory traversal or file-download-by-path endpoint exists; there
    is NO file-upload endpoint at all (Section 9), so upload-based traversal/XSS
    is not reachable.

FIXED:
  * F1 (HIGH — see Section 11) global rate limiting.
  * F5 (LOW — see Section 8) malformed-signature 500 → deterministic 400.

RESIDUAL (documented):
  * No global exception filter is registered. Nest's default filter does not leak
    stack traces for HttpExceptions, and NODE_ENV is not development in prod, so
    the practical leakage risk is low. Recommendation: add a global filter that
    normalizes 500s to a generic body for defense-in-depth (Section 15).
  * CSRF: the API is token-in-Authorization-header (not cookie-session) for its
    own auth, so classic CSRF does not apply to the JWT-protected routes. If any
    client later moves the refresh token into a cookie, add SameSite + CSRF
    tokens (Section 15).

SECTION 8 — CRYPTOGRAPHY FINDINGS
================================================================================
VERIFIED SECURE:
  * Password/OTP hashing: bcrypt (cost 10) for OTPs; no plaintext secrets at rest.
  * Refresh tokens: SHA-256 hashed at rest; raw value is a uuidv4 CSPRNG value.
  * HMAC everywhere is SHA-256 and every comparison is crypto.timingSafeEqual
    (payment verify, webhook verify, service-identity verify) — no `===` on
    secrets on the hot paths.
  * Service-identity signing uses createHmac + timingSafeEqual + createHash
    (sha256 body hash); replay-protected by nonce + timestamp skew.
  * Redis key construction uses fixed prefixes + server-derived ids
    (auth:ban:<userId>, otp_rate:<phone>, svcid:nonce:<svc>:<nonce>) — no
    injectable/format-string key building.

FIXED:
  * F4 (LOW, CWE-331) OTP modulo bias — rejection sampling (Section 3).
  * F5 (LOW, CWE-347/CWE-248) verifyPayment() and handleWebhook() called
    timingSafeEqual directly on the client-supplied signature. If the signature
    is absent or a different length, Node's timingSafeEqual THROWS (RangeError/
    TypeError) → an unhandled 500. This fails CLOSED (no bypass) but is
    ungraceful and a minor log-flood/DoS vector. Added a type+length pre-check
    that returns a deterministic 400 before the constant-time comparison, on both
    the payment-verify and webhook paths. The valid path is unchanged.

NON-ISSUE (documented):
  * health.controller uses `$queryRawUnsafe('SELECT 1')` — a constant string with
    no interpolation; not injectable. Cosmetic only (could be `$queryRaw`).

SECTION 11 — VULNERABILITY FIXES (WHAT CHANGED & WHY)
================================================================================
F1 — HIGH — Rate limiting was inert (OWASP A04/A07, CWE-307, CWE-770)
  Problem: app.module imported ThrottlerModule and the controllers declared many
  @Throttle() limits (OTP send 3/min, OTP verify 5/min, Google 10/min, withdraw
  5/hour, withdraw-confirm 5/hour, deposit 10/hour), but NO APP_GUARD bound
  ThrottlerGuard — so none of them were ever enforced. OTP brute-force,
  credential stuffing and endpoint DoS were unmitigated at the HTTP layer.
  Fix: bound `{ provide: APP_GUARD, useClass: ThrottlerGuard }` and converted the
  module config to the object form with a `skipIf: () => NODE_ENV === 'test'`.
  All pre-existing @Throttle() limits plus the 100/min global default are now
  actively enforced in dev and production. The skipIf disables throttling ONLY
  inside the automated test harness (both e2e and integration bootstraps set
  NODE_ENV=test) so the 280-test matrix stays deterministic; production is never
  in test mode and is fully rate-limited.

F2 — HIGH — Geo-fencing compliance control silently disabled (A01, CWE-863/639)
  Problem: GeoFencingGuard read `req.user?.id || req.user?.sub`; the JWT strategy
  populates `req.user = { userId }`, so the id was always undefined and the guard
  allowed every authenticated user — including users in Indian states where
  real-money gaming is illegal — onto paid-tournament registration and wallet
  deposit-order creation.
  Fix: read `req.user?.userId` first (legacy keys retained as fallback). The
  banned-state block is now actually enforced.

F3 — MEDIUM — Unvalidated inline request bodies (A03, CWE-20, CWE-915)
  Problem: /auth/link-account, /wallet/kyc/submit and /wallet/bank-details typed
  their @Body() as inline TypeScript object types. The global ValidationPipe
  (whitelist/forbidNonWhitelisted) has no runtime metadata for an inline type, so
  those financial/PII/identity payloads were accepted UNVALIDATED and extra
  fields were NOT stripped (mass-assignment exposure).
  Fix: added three class-validator DTOs — LinkAccountDto (provider enum + bounded
  optional fields, email validated), SubmitKycDto (KycDocType enum + bounded
  strings), AddBankDetailDto (BankAccountType enum + bounded account/IFSC/UPI) —
  and wired them into the controllers. Every field is now type-checked, length-
  bounded and unknown fields are rejected.

F4 — LOW — OTP modulo bias (CWE-331)  — see Section 3/8.
F5 — LOW — Payment/webhook signature length pre-check (CWE-347/248) — see Sec 8.

Every change is a security fix only — no business logic, API contract, DB schema
or architecture was altered.
