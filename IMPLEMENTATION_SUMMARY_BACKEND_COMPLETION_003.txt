Resolve backend implementation item M3: the platform computes authoritative,

2. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------
The leaderboard write was wired into the single authoritative game-completion
path (SessionCompletionService.complete), which is already the one routine that
EVERY completion engine (game-session and free-play) routes through:

  submitResult (game-session / free-play)
    -> SessionCompletionService.complete()      (single authoritative path)
         GAME-001 lifecycle guard
         GAME-002 server-authoritative verification (authoritative score)
         persist authoritative result
         anti-cheat (best-effort)
         events (GAME_COMPLETED + VERIFICATION_PASSED/FAILED)
         webhook (Base Platform)
         >>> LEADER-001 leaderboard update (NEW)
               only if validated && outcome === 'COMPLETED'
               exactly-once per session (Redis setnx marker)
               banned re-check (defense-in-depth)
               -> LeaderboardService.updateScore()  (now LIVE)
                    -> Redis sorted set lb:game:<gameType>:all-time
               -> publish LEADERBOARD_UPDATED event

Verification, ranking rules, Redis structure and idempotency style were all
reused unchanged. The score reaching the leaderboard is always the server-
authoritative score; client-claimed scores are never used. Rejected, flagged and
disqualified sessions, and banned users, never rank.

Result: updateScore() now has a LIVE caller; only verified scores rank; duplicate
ranking is impossible; banned/disqualified/rejected never rank. M3 = RESOLVED
(see §19).

6. LEADERBOARD FLOW — BEFORE
--------------------------------------------------------------------------------
  Game/Free-play completion
    -> SessionCompletionService.complete()
         verification -> authoritative score -> persist -> anti-cheat
         -> events -> webhook
         ** RUNTIME ENDS **
  LeaderboardService.updateScore() -> DORMANT (zero callers).
  Global Redis leaderboard (lb:game:<type>:all-time) -> never written from play;
  reads fell back to the DB GameProgress.best_score projection only.


--------------------------------------------------------------------------------
7. LEADERBOARD FLOW — AFTER
--------------------------------------------------------------------------------
  Game/Free-play completion
    -> SessionCompletionService.complete()
         verification -> authoritative score -> persist -> anti-cheat
         -> events -> webhook
         -> [if validated && outcome === 'COMPLETED']
              updateLeaderboard(session, authoritativeScore):
                Redis setnx lb:session:<sessionId>   (exactly-once gate)
                re-check user.is_banned              (defense-in-depth)
                LeaderboardService.updateScore(userId, gameType, score)
                  -> Redis ZADD lb:game:<gameType>:all-time (higher-score-wins)
                publish LEADERBOARD_UPDATED (id leaderboard:<sessionId>)
  Disqualified (tampered/REJECTED) and flagged/unverified sessions skip the block
  entirely; banned users are dropped at the re-check.


--------------------------------------------------------------------------------
8. RUNTIME TRIGGER ADDED
--------------------------------------------------------------------------------
  Trigger: SessionCompletionService.complete(), immediately after the
  authoritative result is committed and the existing events/webhook are emitted.
  This is the single shared completion path for all engines (game-session and
  free-play both call it), so one wiring point covers every authoritative score.
  No new endpoint, cron, queue, or controller was added. The trigger is
  synchronous within completion but best-effort (try/catch) so it can never fail
  or roll back a completed game.


--------------------------------------------------------------------------------
9. SCORE VERIFICATION
--------------------------------------------------------------------------------
  - The leaderboard receives ONLY verdict.authoritativeScore, produced by the
    GAME-002 VerificationPipeline. Client-claimed score is never used.
  - The update runs only when verdict.validated === true (status VERIFIED) AND
    outcome === 'COMPLETED'. A REJECTED/tampered verdict yields
    outcome === 'DISQUALIFIED' and is excluded; any non-VERIFIED (flagged)
    verdict has validated === false and is excluded.
  - Net: rejected sessions never rank; disqualified users never rank;
    unverified/flagged results never rank.


--------------------------------------------------------------------------------
10. IDEMPOTENCY VERIFICATION
--------------------------------------------------------------------------------
  Layer 1 — Lifecycle: complete() runs at most once per session (loaded with
            outcome === null, then transitioned to COMPLETED), so the block is
            naturally reached once per session.
  Layer 2 — Exactly-once marker: Redis setnx lb:session:<sessionId> (7-day TTL)
            makes any re-entry a no-op, so a session can rank at most once even
            under retries/races.
  Layer 3 — Ranking semantics: updateScore is higher-score-wins (ZADD only when
            the new score exceeds the stored one), so re-applying the same
            session's score is itself a no-op.
  Layer 4 — Event dedup: LEADERBOARD_UPDATED uses deterministic id
            leaderboard:<sessionId>, which the event bus de-duplicates.
  Result:   "Every verified score updates the leaderboard exactly once;
            duplicate updates are impossible."


--------------------------------------------------------------------------------
11. REDIS FLOW
--------------------------------------------------------------------------------
  - Exactly-once marker: SETNX lb:session:<sessionId> '1' then EXPIRE 7d.
  - Leaderboard write (existing, unchanged): ZSCORE then ZADD
    lb:game:<gameType>:all-time <score> <userId> (only if higher).
  - Reads (existing, unchanged): ZREVRANGE/ZREVRANK/ZSCORE on the same key, with
    a DB GameProgress fallback. The dormant Redis sorted set is now populated
    from real authoritative play, so live rankings reflect actual results.
  No Redis key schema or ranking rule was changed.

  - Existing GAME_COMPLETED / VERIFICATION_* events are unchanged.
