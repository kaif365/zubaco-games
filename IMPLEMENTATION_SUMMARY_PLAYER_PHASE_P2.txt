6. TOURNAMENT INTEGRATION
───────────────────────────────────────────────────────────────────────────────
Screen: src/screens/main/TournamentScreen.tsx

Season list (React Query key ['seasons']):
  • GET /tournament/seasons → Season[] (status REGISTRATION | ACTIVE).
  • Each card shows: name, status badge, description, prize pool (₹), entry fee
    (or "Free entry"), player count (_count.entries [/ max_players]), and the
    start–end date range.
  • States: loading spinner · error + Retry · empty ("No active tournaments")
    · pull-to-refresh (RefreshControl bound to isFetching/refetch).

Season detail sheet (modal, opened by tapping a card):
  • Registration status (React Query key ['seasonStatus', seasonId], retry:false
    so a 404 is treated as "not registered" rather than an error toast).
  • If NOT registered → Register button:
      POST /tournament/seasons/:id/register (mutation).
      onSuccess invalidates ['seasons'], ['seasonStatus', id] and ['wallet']
      (entry fee may have been debited), and confirms via Alert.
      Button label shows the entry fee when the season is paid.
  • If registered → shows the player's EntryStatus badge (ACTIVE / ELIMINATED /
    WINNER / WITHDRAWN) and every stage with its games.
      - For each StageGame: shows a "Play" button only when the stage is OPEN,
        the game has not already been completed, and the player is not
        eliminated; otherwise shows the completed score (✓ N) or a lock icon.
      - Play launches a REAL session:
          POST /tournament/seasons/:id/stages/:n/games/:order/start
          → { session_id, game_type, server_seed, config }.
        The access token is fetched from Keychain (SecureStorage.getAccessToken)
        and the WebView is opened via navigation.navigate('Game', …) with
        mode:'TOURNAMENT', seasonId, stageNumber and gameOrder so the completion
        handler can submit to the correct endpoint.

Game type → display name / icon / URL is resolved from the shared GAME_CATALOG
(src/constants/games.ts); dev uses localhost:<devPort>, prod uses
https://game.zubaco.com/<slug>.

7. LEADERBOARD INTEGRATION
───────────────────────────────────────────────────────────────────────────────
Screen: src/screens/main/LeaderboardScreen.tsx

The backend leaderboard is per-GAME (there is no cross-game global endpoint), so
the screen provides:
  • A horizontal game selector chip row (all 19 games from GAME_CATALOG).
  • Two tabs: Global and Friends.
  • A "Your rank" card:
      GET /leaderboard/game/:type/me → { rank, score }  (key ['myRank', type]).
      Shows "#rank · score pts" or "Unranked — play to get on the board".
  • Global tab (useInfiniteQuery key ['leaderboard', type]):
      GET /leaderboard/game/:type?page=N → LeaderboardEntry[].
      Pagination: getNextPageParam requests the next page while the last page
      returned a full 50 rows; onEndReached triggers fetchNextPage; a footer
      spinner shows while fetching the next page.
  • Friends tab (useQuery key ['friendsLeaderboard', type], enabled only on tab):
      GET /leaderboard/game/:type/friends → LeaderboardEntry[] (includes is_me).
  • Each row: rank (🥇/🥈/🥉 for top 3, else #N), avatar (image or initial
    fallback), display name (self flagged "(You)" and highlighted), optional
    "Level N", and score.
  • States: loading · error + Retry · empty (game-specific / friends-specific
    copy) · pull-to-refresh (refetches the active list AND the player's rank).

Note: the backend exposes no leaderboard text-search endpoint, so no search box
was added (would have required faking client-side search over a paged list).

8. GAME SESSION FLOW
───────────────────────────────────────────────────────────────────────────────
Screen: src/screens/game/GameScreen.tsx (single WebView host for all modes).

Launch (session created server-side BEFORE the WebView opens — no placeholder
session id ever reaches the game):
  • FREE_PLAY  — FreePlayScreen  → POST /free-play/start
  • TOURNAMENT — TournamentScreen→ POST /tournament/…/start
  • CHALLENGE  — (challengeId + session supplied by caller)

The real access token (Keychain) and real session_id are injected into the
WebView via window.__ZUBACO__ = { token, gameSessionId, platform:'mobile' }.

Completion (WebView posts { type:'GAME_COMPLETED', score, duration_ms }):
  • mode==='TOURNAMENT' → POST /tournament/submit { session_id, score,
    duration_ms }; then invalidate ['seasons'], ['seasonStatus', seasonId],
    and (if gameType known) ['leaderboard', gameType] + ['myRank', gameType].
  • mode==='CHALLENGE'  → POST /social/challenges/:id/submit { session_id,
    score }; then invalidate ['challenges'].
  • mode==='FREE_PLAY'  → POST /free-play/submit { session_id, score,
    duration_ms }; then invalidate ['progress'], ['energy'] and
    ['leaderboard'/'myRank', gameType].
  • Submission is best-effort: errors are swallowed (the server may already have
    finalised the session), and navigation.goBack() always runs in .finally().

Server-side authority (unchanged, backend): both /free-play/submit and
/tournament/submit route through the single SessionCompletionService which
recomputes the authoritative score, persists it, runs anti-cheat, emits events
and (tournament) updates the StageEntry totals. The client's reported score is a
claim only. This preserves the existing security model.

Challenge mode: the backend Challenge flow (createChallenge / acceptChallenge /
submitChallengeScore) reuses free-play-style sessions and has NO dedicated
mobile screen today. GameScreen and the API client now fully support the
CHALLENGE submit path so a future Challenge UI can drive it without further
GameScreen changes. See §18.

9. BACKEND APIs CONNECTED
───────────────────────────────────────────────────────────────────────────────
Tournament (TournamentController @ /api/v1/tournament):
  GET  /seasons                                   → Season[]
  POST /seasons/:id/register                      → { entry_id, season, cohort,
                                                       registration_week }
  GET  /seasons/:id/status                        → { status(EntryStatus),
                                                       season, stages(StageEntry[]) }
  POST /seasons/:id/stages/:n/games/:order/start  → { session_id, game_type,
                                                       server_seed, config }
  POST /submit  { session_id, score, duration_ms }→ { score, total_score }

Leaderboard (LeaderboardController @ /api/v1/leaderboard):
  GET  /game/:type?page=N       → LeaderboardEntry[]  ({rank,user,score,
                                                        highest_level?})
  GET  /game/:type/me           → { rank, score }     (nullable)
  GET  /game/:type/friends      → LeaderboardEntry[]  (+ is_me)

Social / Challenge (SocialController @ /api/v1/social):
  POST /challenges/:id/submit  { session_id, score } → challenge update

Free Play (unchanged, reused for cache-invalidation correctness):
  POST /free-play/start, POST /free-play/submit, GET /free-play/energy,
  GET /free-play/progress

TypeScript interfaces added to src/services/api.ts (exact backend shapes):
  SeasonStatus, StageStatus, EntryStatus, SessionOutcome (unions),
  StageGame, SeasonStage, Season (incl. _count.entries),
  RegisterResult, StageEntrySession, StageEntry, SeasonStatusResult,
  StartTournamentResult, SubmitTournamentResult,
  LeaderboardUser, LeaderboardEntry, MyRank.

12. SESSION VERIFICATION
───────────────────────────────────────────────────────────────────────────────
  • Sessions are always created by the backend before the WebView opens; the
    WebView receives a real session_id + real bearer token (no 'pending'/''
    placeholders from the P2 launch paths).
  • The completion handler submits to the endpoint matching the launch mode,
    guaranteeing the session id is finalised by the same subsystem that created
    it.
  • Duplicate-play protection is enforced server-side (startTournamentGame throws
    "Already played this game in this stage"); the UI additionally hides the Play
    button for already-completed stage games.
  • Score is server-authoritative; the client value is treated as a claim only.

13. REACT QUERY INTEGRATION
───────────────────────────────────────────────────────────────────────────────
Query keys:
  ['seasons']                        — active season list
  ['seasonStatus', seasonId]         — per-season registration/stage status
  ['leaderboard', gameType]          — global leaderboard (useInfiniteQuery)
  ['myRank', gameType]               — player's own rank
  ['friendsLeaderboard', gameType]   — friends leaderboard
  ['progress'] / ['energy']          — free-play (reused from P1)
  ['challenges']                     — invalidated after challenge submit
Mutations: registerForSeason, startTournamentGame, and the (mode-based) result
submissions in GameScreen.
Invalidations wired so a completed game immediately refreshes tournament status,
leaderboards, the player's rank, and free-play progress/energy without manual
refetch. Uses the existing global QueryClient (retry:2, staleTime:30000); no new
client or provider was introduced.
