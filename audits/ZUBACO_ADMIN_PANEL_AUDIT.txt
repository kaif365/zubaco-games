================================================================================
PHASE 1 — ADMIN AUTHENTICATION
================================================================================
Login: POST /admin/auth/login  (admin-auth.controller, @Public, HttpCode 200)
  admin-auth.service.login(email, password):
    prisma.admin.findFirst({ email, deleted_at:null })
    verifyPassword(password, admin.password)   (admin/password.util)
    generateLoginToken(admin.id, USER_TYPES.ADMIN, sessionId)  -> JWT
    persists adminAccessToken row (access_token, session_id, expires_at = +7d)
    writes Redis session + admin cache (TTL = TOKEN_EXPIRY.LOGIN = 7d)
  logout: deletes the token row(s) + Redis session.
  me    : returns the cached admin.

FINDINGS
  1.1  NO MFA / 2FA of any kind. Email + password is the only factor for the
       highest-privilege console.
  1.2  NO brute-force protection. @nestjs/throttler is not a dependency and no
       per-account lockout/backoff exists; /admin/auth/login can be hammered.
  1.3  NO login/logout audit trail. The audit interceptor explicitly SKIPS any
       path containing '/auth/', so admin sign-in, sign-out and failed logins
       are never recorded anywhere.
  1.4  7-day non-rotating bearer token. The session token lives 7 days with no
       refresh/rotation and no idle timeout; a captured token is replayable for
       the full window. The only revocation paths are (a) per-session logout and
       (b) soft-deleting the admin (deleted_at), which the guard re-checks.
  1.5  No admin provisioning surface. The admin module exposes only auth — there
       is no create/disable/rotate-admin endpoint; admins are managed by direct
       DB writes, so there is no audited account-lifecycle.

PHASE 2 — AUTHORIZATION / RBAC / PRIVILEGE ESCALATION
================================================================================
Global guard: src/common/guards/session.guard.ts (APP_GUARD)

  const requirements = reflector.getAllAndOverride(SESSION_METADATA_KEY, [
      handler, class ]);
  if (!requirements) { return true; }          <-- FAIL OPEN

  When requirements DO exist: extract Bearer token -> verifyToken -> check
  tokenType ∈ requirements.tokenTypes and userType ∈ requirements.userTypes,
  then admin fast-path (Redis session) | DB fallback (adminAccessToken where
  expires_at > now) re-validating admin.deleted_at = null. On success it sets
  request[REQUEST_CONTEXT.SESSION] = { sessionId, userId, userType, tokenType }
  and request[REQUEST_CONTEXT.ADMIN] = <admin>.

FINDINGS
  2.1  FAIL-OPEN DEFAULT. Any handler that carries neither @RequireSession nor
       @Public is allowed through with NO authentication, because the guard
       returns true when no requirement metadata is found. Security is
       therefore opt-in per controller/handler, the inverse of safe default.
  2.2  THREE FULLY ANONYMOUS CONTROLLERS (consequence of 2.1):
         • prizes   (@Controller('admin/prizes'))  — no decorators
         • exports  (@Controller('admin/exports')) — no decorators
         • banners  (@Controller('admin/banners')) — no decorators
       Every route on these three controllers is reachable WITHOUT a token.
       Impact detailed in Phases 3/5.
  2.3  NO RBAC. The Admin model (prisma/schema.prisma) has NO role / permission /
       scope field:
         model Admin { id email password access_tokens audit_logs created_at
                       updated_at deleted_at }
       The ONLY authorization check anywhere is userType === ADMIN (constant 2).
       Therefore every authenticated admin has identical, total power: edit any
       user, credit/debit any wallet, distribute prizes, run eliminations,
       change TDS/fee settings, ban/unban — with no separation of duties, no
       maker-checker, no least privilege, no read-only/support tier.
  2.4  NO horizontal scoping. There is no notion of "this admin may act on this
       tenant/season"; the userType gate is binary.
  2.5  Cross-service privilege: admin actions that reach the platform
       (cheat-flags proxy, Phase 6) are trusted by the platform purely via the
       shared INTERNAL_API_KEY with a body-supplied admin_id — i.e. the platform
       cannot independently authenticate which admin acted (governing strategic
       blockers AUTH-002 / AUTH-003).

PHASE 3 — USER MANAGEMENT
================================================================================
src/users/users.controller.ts — class-level @RequireSession({LOGIN, ADMIN})
(covers all 9 routes; reflector.getAllAndOverride matches the class). So unlike
prizes/exports/banners, user management IS authenticated — but governed by the
no-RBAC, broken-audit context above.

users.service.ts:
  banUser(userId, reason)   -> user.update is_banned=true, ban_reason=reason
  unbanUser(userId)         -> is_banned=false, ban_reason=null
  creditWallet(userId,amt,reason)  guard amt>0
        wallet.upsert(create balance=amt | update increment amt)
        transaction.create(type DEPOSIT, status COMPLETED,
                            balance_after, "Admin credit: <reason>")
  debitWallet(userId,amt,reason)   guard amt>0
        read wallet; if balance < amt throw; wallet.update decrement
        transaction.create(type WITHDRAWAL, status COMPLETED, "Admin debit: ...")
  updateUser(userId,data)   whitelist [display_name, username, is_verified]

FINDINGS
  3.1  Direct real-money mutation. creditWallet/debitWallet write the shared
       wallet + transaction tables directly, bypassing the platform wallet
       service entirely: no idempotency key, no ledger entry pairing, no TDS,
       no payout pipeline, and bonus_balance is ignored (balance_after reflects
       cash only). Manifestation of WALLET-002 on the admin side.
  3.2  Type laundering. An admin credit is persisted as type DEPOSIT and an
       admin debit as type WITHDRAWAL — there is no distinct ADMIN_CREDIT /
       ADMIN_ADJUSTMENT type. These rows pollute deposit/withdrawal analytics
       and the reconciliation set, and an admin "debit" never goes through KYC/
       TDS/disbursement yet looks like a real withdrawal.
  3.3  debitWallet TOCTOU. The "balance < amount" check is read-then-write and
       is not performed under a row lock; concurrent debits can race past the
       guard (the decrement itself is atomic, but the sufficiency check is not).
  3.4  Ban is inert beyond the flag. banUser only sets is_banned/ban_reason. It
       does NOT revoke the user's active sessions/tokens, does NOT remove
       persisted scores or leaderboard entries, does NOT eliminate the user from
       in-flight tournaments, and prize selection has no is_banned filter — so a
       banned user can still rank and be paid (governing blocker ACHEAT-001).
  3.5  is_verified is admin-settable via updateUser with no KYC evidence trail —
       a verification/compliance flag can be flipped at will and (per Phase 8)
       without any recorded actor.
  3.6  No user deletion / data-subject erasure / account-recovery path exists in
       the service (only ban). Relevant for DPDPA right-to-erasure obligations.

PHASE 4 — TOURNAMENT / SEASON CONTROL PLANE
================================================================================
seasons.controller.ts (@RequireSession class-level) -> seasons.service.ts:
  createSeason            status seeded 'UPCOMING'
  updateSeason            whitelist [name, description, start_date, end_date,
                          prize_pool, entry_fee, max_players, status]
  createStage             elimination_pct default 50.0, status 'LOCKED'
  updateStage             whitelist [name, open_date, close_date,
                          elimination_pct, status]
  openStage(id)           status -> 'OPEN'
  closeStage(id)          status -> 'CLOSED'
  triggerElimination(id)  requires stage.status==='CLOSED'; eliminateCount =
                          floor(totalPlayers * elimination_pct/100); ranks
                          players, sets {rank, eliminated} on stage entries and
                          season_entry status 'ELIMINATED' for the tail slice.
tournaments.service.ts   create/update with StatusSchema enum
                          (ACTIVE|INACTIVE|DEACTIVATE).

FINDINGS
  4.1  Second elimination/ranking control plane. triggerElimination is a manual
       admin reimplementation of stage progression that writes the same
       stage-entry rank/eliminated fields and season_entry status as the
       platform's own pipeline — divergent dual control planes over money-
       bearing qualification (governing blocker TOURN-001).
  4.2  No lifecycle state machine. openStage/closeStage flip status with no
       guard on the current state (an already-CLOSED stage can be re-opened; a
       LOCKED stage can jump straight to OPEN), and triggerElimination has no
       idempotency — re-invoking on the same CLOSED stage re-ranks/re-eliminates
       (governing blocker TOURN-003).
  4.3  Post-registration mutation of money terms. updateSeason can change
       entry_fee / prize_pool / status after a season exists; only some ops are
       gated on status==='UPCOMING'. Editing prize_pool/entry_fee mid-flight has
       no compensation logic for already-charged entrants.
  4.4  Prize distribution is a SEPARATE, unauthenticated, non-idempotent path
       (Phase 5) — elimination and payout are not transactionally linked.

prizes.controller.ts — @Controller('admin/prizes'), NO @RequireSession / NO

prizes.service.distribute(season_id, distributions):
  for each d: wallet.update({ where:user_id, data:{ balance:{increment:amount}}})
              transaction.create(type 'PRIZE_WIN', status 'COMPLETED',
                                  balance_after, metadata {season_id, rank})

FINDINGS  (CRITICAL)
  5.1  UNAUTHENTICATED MONEY CREATION. Because prizes has no auth decorator and
       the guard fails open, ANY anonymous caller can POST arbitrary credits to
       arbitrary user wallets. This is the single most severe finding: direct,
       tokenless, real-money minting.
  5.2  No input validation. The body is a raw inline-typed @Body() (not a
       createZodDto), so the global ZodValidationPipe does not apply. amount is
       unchecked — a negative amount becomes a silent debit (increment of a
       negative), and user_id/season_id are unvalidated.
  5.3  Non-idempotent double-credit. distribute has no idempotency key and no
       guard against re-distribution for the same season/rank; a re-POST credits
       again (the admin half of TOURN-001's double-distribution risk).
  5.4  Ignores bonus split, no row lock, no ledger pairing (WALLET-002); writes
       balance_after pre-read in some paths.
  5.5  No banned-user / eligibility filter — banned cheaters are payable
       (ACHEAT-001).

FINDINGS
  5.6  ANONYMOUS BULK EXFILTRATION of user PII and the full financial

PHASE 6 — ANTI-CHEAT MANAGEMENT
================================================================================
cheat-flags.service.ts (controller @RequireSession class-level):
  Ingest : onModuleInit -> sqs.registerHandler(handleEvent); cheat flags flow
           platform -> SQS -> admin, upserted into cheatFlag (idempotent on
           reference_id). Unknown gameType/game are dropped with a warn.
  List   : listCheatFlags (paginated read).
  Actions (PROXY to platform anti-cheat API via callPlatformApi):
     reviewFlag(flagId, adminId, 'dismiss'|'warn'|'ban')
        -> POST {PLATFORM_API_URL}/anti-cheat/flags/:id/review
           body { action, admin_id: adminId }
     unbanUser(userId)     -> POST /anti-cheat/users/:id/unban
     resetRiskScore(userId)-> POST /anti-cheat/users/:id/reset-risk
  PLATFORM_API_URL/INTERNAL_API_KEY read from env.

FINDINGS
  6.1  Trust boundary is the shared static key. Admin enforcement actions are
       authorized by the platform solely via INTERNAL_API_KEY, with the acting
       admin_id passed in the request BODY — spoofable and non-authoritative on
       the platform side (governing AUTH-002 / AUTH-003).
  6.2  Enforcement actions inherit ACHEAT-001: a 'ban' review does not retract
       persisted scores/leaderboard/StageEntry totals or exclude the user from
       prize selection — detection without enforcement.
  6.3  No appeal workflow. Actions are limited to dismiss/warn/ban + unban/
       reset-risk; there is no structured appeal/override audit record.
  6.4  adminId forwarded to the platform originates from the admin session
       context, but per Phase 8 the same identity is NOT captured in the admin's
       own audit_logs, so the action is attributable on neither side reliably.

PHASE 7 — SYSTEM MANAGEMENT / SETTINGS / SECRETS
================================================================================
settings.service.ts (controller @RequireSession class-level):
  getAll / get(key) ; updateMany([{key,value}]) -> systemSetting.update each.
  Seeds DEFAULT_SETTINGS on boot (upsert, never overwrites existing) including
  money-sensitive keys: platform_fee_pct=10, tds_rate_pct=30,
  min_withdrawal_amount=100, max_daily_deposits=10000, kyc_required_above=10000,
  auto_ban_critical_flags=3, default_stage_elimination_pct=50, etc.

FINDINGS
  7.1  Unvalidated mutation of money/compliance config. updateMany accepts any
       string value for any existing key (no Zod schema, no per-key validation,
       no range/type check). An admin can set tds_rate_pct or platform_fee_pct
       to any string; the value column is untyped text.
  7.2  Authority ambiguity. These settings live in the admin DB's systemSetting
       table; whether the platform actually reads them at money-decision time is
       not enforced in the admin service. If the platform reads them, 7.1 is a
       direct financial-control risk; if it does not, the admin "controls" are
       partly cosmetic — either way it is a correctness gap.
  7.3  No secret management. Cross-service secrets (INTERNAL_API_KEY,
       PLATFORM_API_URL, AWS creds, DB URL) are read from process.env with no
       vault/rotation; INTERNAL_API_KEY defaults to '' if unset (cheat-flags),
       which would silently send an empty-key request rather than fail closed.
  7.4  No feature-flag guard rails / change review on settings mutations
       (compounded by the broken audit trail, Phase 8).

PHASE 8 — AUDIT LOGGING & IMMUTABILITY
================================================================================
src/common/interceptors/audit.interceptor.ts (global APP_INTERCEPTOR):
  Audits only POST/PUT/PATCH/DELETE; skips any '/auth/' path.
  const adminId = request.session?.adminId || request.user?.id || 'unknown';
  ... auditLog.create({ admin_id: adminId, action, entity, entity_id, changes,
                        ip_address }).catch(() => {})   // fire-and-forget

prisma/schema.prisma:
  model AuditLog {
    id String @id ; admin_id String ; action String ; entity String ;
    entity_id String? ; changes Json? @db.JsonB ; ip_address String? ;
    created_at DateTime @default(now()) ;
    admin Admin @relation(fields:[admin_id], references:[id], onDelete:Cascade)
  }   // admin_id is a REQUIRED FK to admins.id

FINDINGS  (CRITICAL)
  8.1  THE AUDIT TRAIL IS NON-FUNCTIONAL — ZERO ROWS ARE EVER WRITTEN.
       The guard stores the actor at request['session'] = { ..., userId, ... }
       (key REQUEST_CONTEXT.SESSION === 'session'), but the interceptor reads
       request.session?.adminId — a property that does not exist on that object
       (it is named userId), and request.user is never set. So adminId always
       resolves to the literal string 'unknown'. admin_id is a REQUIRED foreign
       key to admins.id; inserting 'unknown' violates the FK constraint, the
       auditLog.create() rejects, and the rejection is swallowed by .catch(()=>{}).
       Net effect: NO administrative action is ever recorded. GET /admin/
       audit-logs will always return empty.
  8.2  Even if 8.1 were fixed, GET operations are never audited — so the
       anonymous PII/transaction exports (Phase 5.6) and all read access are
       invisible.
  8.3  Auth events are excluded ('/auth/' skip) — no login/logout/lockout trail.
  8.4  Not immutable. audit_logs is an ordinary table and the admin DB role has
       full DML on the shared database; rows could be UPDATE/DELETE'd. No
       append-only enforcement, no hash chaining, no WORM/off-box sink.
  8.5  No before/after state capture. changes = request.body only (and null for
       DELETE); there is no prior-value snapshot, so even a working log could not
       show what a value changed from.
  8.6  entity_id is extracted only from params.id/seasonId/stageId — routes
       keyed on :userId (the entire users controller) record entity_id = null.
  8.7  Fire-and-forget create — any transient DB error drops the record silently
       (lossy by design).

PHASE 9 — SECURITY (CSRF / XSS / VALIDATION / DANGEROUS MUTATIONS)
================================================================================
  9.1  Authentication bypass — see 2.1/2.2/5.1/5.6/5.7: anonymous money
       creation, PII/financial export, and content CRUD. Highest severity.
  9.2  CSRF: low risk — the API authenticates via Authorization: Bearer (not
       cookies), so cross-site form posts cannot ride ambient credentials. No
       csurf layer exists, which is acceptable ONLY while auth stays header-based
       (do not migrate to cookie sessions without adding CSRF defense).
  9.3  Stored XSS: banners create/update accept raw @Body() with no
       sanitization (5.7); any HTML/script persisted is rendered by the banner
       consumer. Validate/encode at the boundary.
  9.4  Input validation gap: the global ZodValidationPipe only validates
       createZodDto bodies. Handlers using raw inline-typed @Body() — prizes,
       banners, users credit/debit, settings updateMany — receive UNVALIDATED
       input (negative amounts, type coercion, unexpected keys).
  9.5  Dangerous mutations without confirmation/maker-checker: prize distribute,
       wallet credit/debit, triggerElimination, ban, and TDS/fee settings are
       single-call, single-actor, irreversible money/qualification operations
       with no second-approver and (per Phase 8) no record.
  9.6  helmet enabled and CORS is allow-list driven (ADMIN_CORS_ORIGINS) — the
       only two solid security controls present.
  9.7  No rate limiting anywhere (no throttler) — login brute force (1.2) and
       export/mutation flooding are unthrottled.
