1. OBJECTIVE
--------------------------------------------------------------------------------
Eliminate the single remaining backend implementation item from the Backend
Certification Audit: deposit-order creation was idempotent ONLY when the client
supplied an `Idempotency-Key` header. A header-less retry could create a second
Razorpay order (the ledger already prevented duplicate credits, but a duplicate
unpaid ORDER was still possible). After M10 the guarantee must hold for ALL
clients: one logical deposit intent -> exactly one Razorpay order.


--------------------------------------------------------------------------------
2. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------
Implemented OPTION A (server-derived deterministic idempotency key). When the
client omits `Idempotency-Key`, the server now derives a deterministic key from
the logical deposit intent (userId + amountPaise + currency). A header-less,
concurrent or post-crash retry of the same intent collapses onto the SAME open
order instead of minting a new one. Two layers enforce this:

  Layer 1 (fast)    Redis idempotency map  deposit:order:idem:<userId>:<key>
                    + setnx in-flight lock for concurrency.
  Layer 2 (durable) open-PENDING DB lookup (Transaction, user+amount, within the
                    checkout window) — survives a Redis flush.

A previously-mapped order is replayed ONLY while it is still OPEN (PENDING); a
COMPLETED/FAILED/CANCELLED order is never replayed, so a user may legitimately
deposit the same amount again once a prior intent has resolved. The client
header path is preserved and remains fully supported (now namespaced `client:`).

No database schema change, no API breaking change, no change to the ledger,
webhook, settlement, wallet or events. Build GREEN.

7. NEW DEPOSIT ORDER FLOW
--------------------------------------------------------------------------------
  createDepositOrder(userId, amount, idempotencyKey?)
    amountPaise = round(amount*100); currency = 'INR'
    effectiveKey = idempotencyKey ? "client:<key>"
                                  : "auto:" + sha256(userId|amountPaise|currency)[:32]
    idemMapKey = deposit:order:idem:<userId>:<effectiveKey>

    (1) FAST PATH
        mapped = Redis get idemMapKey
        if mapped and order still PENDING -> return replay (SAME order)

    (2) CONCURRENCY GUARD
        setnx idemMapKey:lock
        if not acquired:
            re-read map; if mapped+PENDING -> return replay
            else throw 409 ConflictException
        expire lock 30s

    try:
      (3) DURABLE BACKSTOP (Redis-flush safe)
          findReusableOpenDeposit(user, amount, 900s)
          if found -> set map -> return existing order

      (4) CREATE
          createRazorpayOrder(amountPaise, currency, notes, effectiveKey)
          ledger.createPendingDeposit(order.id)   (unchanged, idempotent)
          Redis set map = order.id (TTL 900)
          return order
    finally:
          Redis del idemMapKey:lock

  Result: one logical intent -> exactly one open order, for EVERY client.


--------------------------------------------------------------------------------
8. IDEMPOTENCY STRATEGY CHOSEN
--------------------------------------------------------------------------------
  OPTION A — Server-derived deterministic idempotency key (preferred).

  - Header optional and backward compatible. Present header => "client:<key>"
    (exact prior behaviour, just namespaced). Absent header => deterministic
    "auto:<sha256(userId|amountPaise|currency)>".
  - Dedup window = 900s (DEPOSIT_ORDER_WINDOW_SECONDS), inside the 30-min
    WalletCleanupService abandonment window, so an unpaid order is reused while
    open and cleaned up afterwards.
  - Replay is gated on status === 'PENDING' so a resolved (paid/failed/cancelled)
    intent does NOT block a new legitimate deposit of the same amount.
  - Durable DB backstop guarantees the property even if Redis is flushed.


--------------------------------------------------------------------------------
9. WHY THIS STRATEGY WAS CHOSEN
--------------------------------------------------------------------------------
  - Option B (reject requests without a header) is an API breaking change for
    existing clients and shifts correctness onto every caller; the brief allows
    it ONLY if server-side generation is impossible. It is not impossible here.
  - Option A keeps the public contract unchanged (header still honoured), removes
    the gap for header-less clients, and is the industry-standard pattern
    (deterministic key + short window + state-gated replay).
  - The two-layer design (Redis + DB) makes the guarantee hold under header-less,
    concurrent AND crash/Redis-loss conditions without a schema change.

10. RUNTIME VERIFICATION
--------------------------------------------------------------------------------
  Repeated request (same user, same amount, same intent):
    - 1st call mints order O1, maps it, registers PENDING.
    - 2nd call (header-less): same derived key -> Redis fast path hits O1
      (still PENDING) -> returns O1 with idempotent_replay: true. No 2nd order.
  Different amount by same user -> different derived key -> new order (correct,
  it is a different logical intent).
  Same amount AFTER O1 is paid/failed/cancelled -> replay gate (status!==PENDING)
  returns null -> a new order is correctly created (legitimate re-deposit).
