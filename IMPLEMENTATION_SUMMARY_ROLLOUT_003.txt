1. OBJECTIVE
--------------------------------------------------------------------------------
Integrate the authoritative TournamentOrchestrator and WalletLedgerService into
the LIVE production execution path, replacing remaining legacy runtime money and
progression paths so that:
  (1) Tournament progression flows only through TournamentOrchestrator.
  (2) Money credits flow through WalletLedgerService (the authoritative money
      engine); legacy WalletService remains only as a compatibility adapter.
  (3) Reward eligibility flows through the authoritative tournament pipeline
      (no duplicate rewards / payouts).
  (4) Payout reversal paths use EnforcementService + WalletLedger.
  (5) Idempotency holds across tournament progression and wallet operations.

KEY FINDING THAT SHAPED THIS PHASE: in the canonical repo the live runtime is
ALREADY routed through the authoritative services for every operator-driven
money/progression action (this was the result of ROLLOUT-001's admin control
plane and ROLLOUT-002's unified completion pipeline). There was NO remaining
in-repo LIVE legacy *progression* path and NO live legacy *reward-credit* path
to replace. What remained was one direct-mutation reward-credit method on
WalletService (creditPrize) plus several user-facing money methods that cannot
be moved to the current ledger without semantic/settlement regressions. This
phase hardened the prize-credit path onto the ledger and verified the rest.

9. REMAINING LEGACY PATHS (STILL ON WalletService — WITH REASONS)
--------------------------------------------------------------------------------
These remain direct WalletService mutations BY DESIGN this phase, because moving
them to the current ledger would cause a regression rather than an improvement:

- creditReferralBonus (LIVE, social referral): credits the BONUS bucket with
  transaction type REFERRAL_BONUS. The ledger's credit operations map to type
  'PRIZE_WIN'; routing referral through it would relabel the row AND (because the
  daily reconciliation aggregates 'PRIZE_WIN' against the CASH balance only)
  would manufacture false reconciliation discrepancies. Blocked until the ledger
  gains a referral/bonus-credit operation + txType mapping (architecture change,
  out of scope).

- deposit (LEGACY adapter; the LIVE deposit path is
  PaymentGatewayService.creditDepositAtomically): the live deposit flow pre-
  creates a PENDING DEPOSIT row and atomically claims it (PENDING -> COMPLETED).
  ledger.post creates a fresh COMPLETED row instead, which would double-count.
  Model mismatch — out of scope for a money-safe change this phase.

- deductEntryFee (LIVE, tournament registration): an ENTRY_FEE debit. The ledger
  has no entry-fee debit operation; the nearest (ADJUSTMENT negative) relabels
  the row to 'WITHDRAWAL', corrupting reconciliation semantics. Blocked on a
  ledger entry-fee operation (architecture change, out of scope).

- requestWithdrawal / initiateWithdrawal / confirmWithdrawal (LIVE): create a
  PENDING WITHDRAWAL that settles later. ledger.post forces status COMPLETED, so
  routing withdrawal through it would mark funds settled before disbursement.
  Belongs to the WALLET-001 settlement pipeline (PENDING_PAYOUT/PAYOUT_SETTLEMENT
  + RazorpayX), a separate phase.

- EnforcementService payout reversal currently emits the external webhook only;
  it does not also call ledger.post(PAYOUT_REVERSAL). Wiring an internal reversal
  here without first cancelling the original PENDING withdrawal row would
  double-pay (re-credit + later settlement). Requires a ledger "reverse pending
  withdrawal" operation (cancel PENDING + re-credit atomically) — WALLET-001.
