--------------------------------------------------------------------------------
1. OBJECTIVE
--------------------------------------------------------------------------------
Make EventBusService the authoritative event publisher by connecting every
remaining live runtime producer and the remaining supported subscribers, WITHOUT
redesigning the EventBus, notifications, or the webhook integration.

At phase start the bus already had: envelope, versioning, Redis outbox, retry,
DLQ, in-app subscriber, and wallet event publication. The unconnected producers
were: tournament progression, tournament completion, reward eligibility,
anti-cheat enforcement, account review. The unbuilt subscribers were: webhook,
email, SMS, push.


--------------------------------------------------------------------------------
2. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------
Producers (PART A): all five missing live producers now publish through the bus,
post-commit, with deterministic idempotency keys:
  - TournamentOrchestrator.advanceStage()      -> TOURNAMENT_PROGRESSED,
                                                  TOURNAMENT_COMPLETED
  - TournamentOrchestrator.resolveRewardEligibility() -> REWARD_ELIGIBLE (per winner)
  - EnforcementService.enforce()               -> ANTI_CHEAT_ENFORCED (confirmed)
                                                  ACCOUNT_REVIEWED (mark-for-review)
After this phase, EVERY value in PlatformEventType has a live producer that
publishes through EventBusService.

Subscribers (PART B): a Webhook subscriber was added, reusing the existing
durable, HMAC-signed webhook outbox (retry + DLQ). It forwards platform events to
the Base Platform via a new additive 'platform.event' envelope type, idempotent
on the platform event id, and config-gated (no-op when no webhook URL is set).
Email and SMS subscribers were NOT built — there is no email infrastructure at
all, and the only SMS sender (auth OTP) is not a notification channel; wiring
either would require new infrastructure / module coupling, i.e. a redesign,
which is explicitly out of scope. Push is already delivered today through the
in-app subscriber (NotificationService.sendNotification -> FCM
sendPushNotification), so a separate push subscriber was intentionally NOT added
(it would double-send).

Outbox -> retry -> DLQ -> subscriber works unchanged for every newly connected
producer (they all use the same publish() path). Duplicate publication is
prevented by the bus dedupe (Redis setnx on event.id, 7-day) plus deterministic
event ids; producer-level idempotency (tournament advance lock, enforce lock,
ledger claims) prevents re-entry upstream.

Build is GREEN.

10. RUNTIME EVENT FLOW — BEFORE
--------------------------------------------------------------------------------
  Producer (wallet, game session)
      -> EventBusService.publish()
      -> Redis outbox (per subscriber)
      -> drain cron (retry/backoff, DLQ)
      -> InAppEventSubscriber
      -> NotificationService (in-app row + FCM push)

  Tournament progression/completion, reward eligibility, and enforcement did
  NOT enter this pipeline (no publish call).

  (Separately, WebhookService delivered game.result.validated and
   enforcement.reversal to the Base Platform via direct calls — not via the bus.)


--------------------------------------------------------------------------------
11. RUNTIME EVENT FLOW — AFTER
--------------------------------------------------------------------------------
  Producer (wallet, game session, tournament orchestrator, enforcement)
      -> EventBusService.publish(type, data, userId?, deterministicId)
      -> dedupe on event.id (Redis setnx, 7-day) — duplicate publish suppressed
      -> Redis outbox: one record per subscriber  (events:outbox)
      -> drain cron every 10s (claim by zrem, exp backoff, DLQ after 8 attempts)
      -> Subscribers:
           in-app  -> NotificationService -> in-app notification + FCM push
           webhook -> WebhookService.emitPlatformEvent()
                       -> webhook outbox (events: webhook:outbox)
                       -> webhook drain cron (HMAC-signed POST, retry, DLQ)
                       -> Base Platform

  Per live event today:
    GAME_COMPLETED .............. game session  -> bus -> in-app(+push) -> webhook
    VERIFICATION_PASSED/FAILED .. game session  -> bus -> (in-app only if mapped) -> webhook
    WALLET_CREDITED ............. wallet/admin   -> bus -> in-app(+push) -> webhook
    PAYOUT_SETTLED/REVERSED ..... wallet         -> bus -> in-app(+push) -> webhook
    TOURNAMENT_PROGRESSED ....... orchestrator   -> bus -> webhook (no userId -> no in-app)
    TOURNAMENT_COMPLETED ........ orchestrator   -> bus -> webhook (no userId -> no in-app)
    REWARD_ELIGIBLE ............. orchestrator   -> bus -> in-app(+push) -> webhook
    ANTI_CHEAT_ENFORCED ......... enforcement    -> bus -> in-app(+push) -> webhook
    ACCOUNT_REVIEWED ............ enforcement    -> bus -> in-app(+push) -> webhook

18. SECURITY IMPROVEMENTS
--------------------------------------------------------------------------------
  - Single authoritative event plane: tournament, reward, and enforcement
    lifecycle changes now emit through one audited, deduped pipeline rather than
    silently mutating state with no signal.
  - Idempotent publication: deterministic event ids + Redis setnx dedupe make
    duplicate publication impossible even under retries/concurrency.
  - Webhook forwarding reuses the existing HMAC-SHA256 signed envelope; the Base
    Platform can verify origin and dedupe on the (now event-derived) envelope id.
  - Post-commit emission only: every new publish runs after the authoritative DB
    transaction/operation has committed, so no event can describe rolled-back state.

25. KNOWN LIMITATIONS
--------------------------------------------------------------------------------
  - In-app subscriber is at-least-once, not exactly-once: it stamps event_id into
    notification metadata but does not dedupe on it, so a delivery retry after a
    partial failure could create a duplicate in-app notification/push. This is a
    PRE-EXISTING property of InAppEventSubscriber, unchanged by this phase. The
    bus still publishes once; only redelivery on subscriber failure is affected.
  - Webhook subscriber forwards ALL platform events under 'platform.event'. For
    game results and enforcement reversals the Base Platform may also receive the
    pre-existing dedicated webhooks (game.result.validated / enforcement.reversal);
    these are distinct envelope types and the Base Platform dedupes per id.
  - Tournament-wide events carry no userId (see §23).
  - Migrations cannot be applied against the dummy DB; correctness verified by
    compile + reachability/DI review, not runtime execution.
