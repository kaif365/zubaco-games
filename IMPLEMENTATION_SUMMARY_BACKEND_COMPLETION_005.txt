2. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------
All five items are implemented and the build is GREEN.

  - M5: The deposit lifecycle is now fully ledger-governed. New ledger methods
    createPendingDeposit / failDeposit / cancelDeposit own the PENDING, FAILED
    and CANCELLED transitions atomically and idempotently, each writing an
    immutable _ledger audit block. The gateway and the cleanup cron no longer
    write the transaction table directly. FAILED and CANCELLED now publish
    DEPOSIT_FAILED / DEPOSIT_CANCELLED events. Settlement (PENDING -> COMPLETED +
    credit + WALLET_CREDITED) was already ledger-authoritative and is unchanged.

  - M6: createRazorpayXPayout now uses the withdrawal transaction id as a stable
    reference_id AND sends the X-Payout-Idempotency header keyed on the same id.
    A crash-retry re-sends the identical key, so RazorpayX returns the existing
    payout instead of creating a duplicate external transfer.

  - M7: createDepositOrder accepts an optional Idempotency-Key header. A retried
    request short-circuits via a Redis idempotency map and returns the SAME
    Razorpay order; a setnx guard collapses concurrent double-submits. The PENDING
    row is additionally idempotent per order id at the ledger boundary.

  - M8: JwtStrategy.validate now performs an authoritative is_banned check on
    every authenticated request (Redis fast-path backed by the User.is_banned
    column, with back-fill). A banned user's still-valid access token is rejected
    with 403 immediately. EnforcementService.enforce/reverse proactively flip the
    cache so bans/unbans take effect on the next request — reusing the existing
    enforcement engine.

  - M9: WalletService.deposit() had no live caller and is REMOVED. The single
    authoritative deposit runtime is the Razorpay order flow. No dormant deposit
    runtime remains.

6. DEPOSIT FLOW BEFORE
--------------------------------------------------------------------------------
  createDepositOrder -> prisma.transaction.create(PENDING) DIRECTLY (locally
    computed balance_after, no ledger_key, no idempotency, no audit block).
  payment.captured/verify -> ledger.settleDeposit (authoritative — OK).
  payment.failed -> prisma.transaction.updateMany(FAILED) DIRECTLY (no audit,
    no event).
  abandoned cleanup -> prisma.transaction.updateMany(CANCELLED) DIRECTLY (no
    per-row audit, no event).
  Result: only the CREDIT was ledger-governed; PENDING/FAILED/CANCELLED bypassed
  the authoritative ledger.


--------------------------------------------------------------------------------
7. DEPOSIT FLOW AFTER
--------------------------------------------------------------------------------
  createDepositOrder
    -> (M7) Idempotency-Key short-circuit (Redis map) — retry returns same order
    -> createRazorpayOrder
    -> ledger.createPendingDeposit  [PENDING row, ledger_key deposit:pending:<id>,
       idempotent per order id (existing-row check + UNIQUE ledger_key + Redis
       lock), _ledger audit block]
  payment.captured / verify
    -> ledger.settleDeposit  [atomic PENDING -> COMPLETED claim, credit cash
       bucket, _ledger audit, ledger_key deposit:<id>]
    -> publish WALLET_CREDITED (deterministic id, deduped)
  payment.failed
    -> ledger.failDeposit  [atomic PENDING -> FAILED claim, _ledger_failure audit,
       idempotent on repeated webhooks]
    -> publish DEPOSIT_FAILED
  abandoned (cron, > 30 min PENDING)
    -> ledger.cancelDeposit  [atomic PENDING -> CANCELLED claim, _ledger_cancellation
       audit, loses cleanly if it races a late settlement]
    -> publish DEPOSIT_CANCELLED
  Result: PENDING, COMPLETED, FAILED and CANCELLED are ALL authoritative,
  idempotent, audited and event-emitting. The ledger is the single deposit writer.

8. RAZORPAYX (PAYOUT) BEFORE
--------------------------------------------------------------------------------
  createRazorpayXPayout(userId, amount, bankDetail):
    reference_id = `wd_${userId}_${Date.now()}`   (NON-stable, time-based)
    no idempotency header
  A crash between payout success and ledger.completeWithdrawal commit left the
  row PENDING; the next disbursement tick re-called the payout with a NEW
  reference_id -> a duplicate EXTERNAL payout was possible.


--------------------------------------------------------------------------------
9. RAZORPAYX (PAYOUT) AFTER
--------------------------------------------------------------------------------
  createRazorpayXPayout(userId, amount, bankDetail, transactionId):
    reference_id = transactionId                  (stable, deterministic)
    header  X-Payout-Idempotency: transactionId   (RazorpayX dedup key)
  A crash-retry re-sends the SAME idempotency key, so RazorpayX returns the
  existing payout rather than creating a second transfer. processWithdrawal passes
  the withdrawal transaction id. The internal ledger remains at-most-once (the
  PENDING claim guards completeWithdrawal/failWithdrawal), so internal AND external
  sides are now both duplicate-safe.

10. RAZORPAY ORDER BEFORE
--------------------------------------------------------------------------------
  createDepositOrder -> createRazorpayOrder with no idempotency.
  A retried create-order request created a brand-new Razorpay order (and, before
  M5, a duplicate PENDING row) every time.


--------------------------------------------------------------------------------
11. RAZORPAY ORDER AFTER
--------------------------------------------------------------------------------
  Client sends an optional `Idempotency-Key` header (standard pattern).
    - First call: setnx guard -> create order -> store Redis map
      `deposit:order:idem:<userId>:<key>` -> order.id (TTL 900s) -> register
      PENDING row.
    - Retry with the same key: short-circuits on the Redis map and returns the
      SAME order (idempotent_replay:true) — NO new Razorpay order is created.
    - Concurrent double-submit with the same key: the setnx lock lets one win;
      the loser gets 409 and, on retry, receives the mapped order.
  Even without the header, the PENDING row is idempotent per order id at the
  ledger boundary, so a given order can never spawn duplicate PENDING rows.


--------------------------------------------------------------------------------
12. JWT BEFORE
--------------------------------------------------------------------------------
  JwtStrategy.validate(payload) => { userId: payload.sub }   (no ban check)
  A user banned mid-session kept a valid access token until expiry (~15 min).
  enforce() deleted refresh tokens (blocking re-issue) but the live access token
  still authorized requests.


--------------------------------------------------------------------------------
13. JWT AFTER
--------------------------------------------------------------------------------
  JwtStrategy.validate(payload):
    - cacheKey = `auth:ban:<userId>`
    - Redis '1' -> 403 ForbiddenException('Account is banned')
    - Redis '0' -> allow
    - cache miss -> SELECT is_banned FROM users (authoritative) -> back-fill cache
      (TTL 60s) -> ban => 403, else allow; missing user => 401
  EnforcementService.enforce() sets the cache to '1' on a confirmed ban;
  reverse() sets it to '0' on un-ban — so the effect is immediate, not deferred
  to refresh expiry. The DB column stays the source of truth, so a Redis flush
  can never let a banned user through for longer than the 60s TTL.

  Auth:               every JwtAuthGuard request -> validate -> is_banned check
                      -> allow | 403.

16. IDEMPOTENCY VERIFICATION
--------------------------------------------------------------------------------
  Deposit PENDING ..... ledger_key `deposit:pending:<orderId>` + existing-row
                        check by (reference_id,type=DEPOSIT) + Redis lock +
                        UNIQUE ledger_key + P2002 collapse. Re-registration is a
                        no-op (duplicate=true).
  Deposit settle ...... atomic PENDING -> COMPLETED claim (claim.count guard);
                        verify+webhook race cannot double-credit.
  Deposit FAILED ...... atomic PENDING -> FAILED claim; repeated webhook no-op.
  Deposit CANCELLED ... atomic PENDING -> CANCELLED claim; loses cleanly to a
                        late settlement.
  Order creation ...... Redis idempotency map keyed on Idempotency-Key + setnx
                        concurrency guard.
  External payout ..... X-Payout-Idempotency + stable reference_id = transactionId
                        (RazorpayX returns the existing payout on retry).
  Withdrawal settle/fail atomic PENDING claim (unchanged, already idempotent).

  hardening item:

  1. [LOW] Header-less deposit order idempotency. M7 makes order creation
     idempotent when the client supplies `Idempotency-Key` (the standard
     contract). A client that omits the header and retries can still create an

     so no double-charge or duplicate credit results). Fully closing this would
     require either mandating the header at the API contract or a server-derived
     dedup key — a product/contract decision, not a correctness gap.
