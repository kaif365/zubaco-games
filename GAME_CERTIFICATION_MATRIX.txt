CROSS-CUTTING FACTS (apply to ALL games unless overridden per game)
  - ARCHITECTURE: each game = standalone NestJS backend + React/Vite (or Next.js)
    frontend. Wallet, Tournament, and the authoritative cross-game Leaderboard are
    DELEGATED TO THE PLATFORM. Game backends publish events (AWS SNS/SQS or BullMQ:
    GAME_COMPLETED / CHEAT_FLAGGED / SCORE_ANOMALY); the platform consumes them and
    owns money/tournament/global-leaderboard. Therefore for every game:
        WalletRuntime = NO (by design)   TournamentRuntime = NO (by design)
        In-app Notifications = NO (event publishing only; delivery delegated)
    These NOs are ARCHITECTURAL, not defects.
  - LEADERBOARD: every game ships an in-memory leaderboard engine
    (engine/leaderboard.ts: submit/getTop/getRank/getAroundUser). It is a local
    helper; the durable/authoritative leaderboard is the platform's. So
    "LeaderboardRuntime" below = "engine present; persistence delegated".
  - SERVER-AUTHORITATIVE: every game regenerates game state from a server seed and
    re-validates the client's submission server-side (move replay / answer
    re-derivation / grid regeneration). Client scores are recomputed, not trusted.
  - VERIFICATION/ANTI-CHEAT: every game flags score divergence + timing anomalies
    (bot-speed detection) and most persist CheatFlags.
  - TESTS EXIST BUT CI DOES NOT RUN THEM: each backend has at least
    test/app.e2e-spec.ts (security/health); several add engine/leaderboard.spec.ts.
    HOWEVER the games CI workflow has NO test step (build only) — so these suites
    are NOT executed in CI. (Cross-cutting gap; tracked in summary.)
  - SECURITY BASELINE (all games): SessionGuard/JWT, HMAC service auth, request/
    response encryption decorator, Zod/class-validator DTOs, seed-based determinism.
