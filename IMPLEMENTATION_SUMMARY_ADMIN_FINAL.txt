--------------------------------------------------------------------------------
1. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------
The ZUBACO admin panel (Next.js App Router frontend at
zubaco-games/zubaco-admin-panel-repo/zubaco-admin-panel/frontend) was audited
end to end and completed against the authoritative backend
(zubaco-admin-panel/backend, NestJS, prefix /admin).

Key finding: contrary to the assumption of pervasive mocks, the panel was
already ~90% wired to real backend endpoints (Users, Anti-Cheat/Cheat-Flags,
Wallets, Tournaments, Seasons, Stages, Games, Notifications, Audit Logs all
call live APIs with React Query, loading/error/empty states, pagination,
search and filters). The genuine remaining defects were concentrated in:
  (a) the Dashboard, which rendered static "chart coming soon" placeholders;
  (b) the Analytics page, which used WRONG endpoint paths/response shapes and
      rendered placeholder "Chart: ..." text instead of charts;
  (c) dead security/mock code: hardcoded demo credentials in config/auth.ts
      and an unused src/mocks/ data folder.

All of the above were fixed. No charting dependency exists in the project and
none could be added (dependencies cannot be installed — see section 16), so
real, dependency-free inline-SVG chart primitives were introduced and wired to
live analytics data. Every modified/created file passes the VS Code TypeScript
language server with zero errors.

Honest scope note: several features listed in the request (e.g. user
sessions/devices/login-history, delete-user, reset-sessions, wallet
payouts/ledger/reversed/failed, standalone leaderboard-admin, notification
delivery/read/push statistics, scheduled notifications, separate
enforcement-history) have NO corresponding backend endpoint. These were NOT
faked; they are listed as backend-gap items in section 18.

STATUS: CODE-COMPLETE for all frontend-actionable items /
BUILD-VERIFICATION-BLOCKED (node_modules cannot be installed — section 16).

6. USER MANAGEMENT
--------------------------------------------------------------------------------
Backed by real endpoints (frontend/src/lib/api/endpoints/users.ts):
- User list: GET /admin/users with search, status filter, page + limit
  (pagination), returning a normalized PaginatedResponse.
- User details: GET /admin/users/:id.
- Ban / Unban: POST /admin/users/:id/ban and /unban.
- User transaction/history views use the real user history endpoints.
Loading, error, empty, pagination, search and status filters are implemented
in the users feature/pages.

Not available on the backend (NOT faked — see section 18): user
sessions, devices, login history, hard delete, reset-sessions, and separate
suspend-vs-ban semantics (backend exposes ban/unban only).

--------------------------------------------------------------------------------
7. ANTI-CHEAT
--------------------------------------------------------------------------------
Backed by real endpoints (frontend/src/lib/api/endpoints/flagged.ts):
- Live cheat queue / reports: GET /admin/cheat-flags (paginated, filter by
  userId), with backend flag-type/severity mapping.
- Review actions: POST /admin/cheat-flags/:id/dismiss | /warn | /ban.
- User-level: POST /admin/cheat-flags/users/:id/unban, /reset-risk;
  GET /admin/cheat-flags/users/:id/risk-score (risk score + penalty tier).
No mock tables. Loading/error/empty/pagination present in the flagged feature.

Not available on the backend: a separate enforcement-history endpoint and a
single-flag detail fetch (fetchFlaggedById returns null by design because the
backend has no per-flag GET). Listed in section 18.

--------------------------------------------------------------------------------
8. WALLET ADMIN

Backed by real endpoints (frontend/src/lib/api/endpoints/wallets.ts):
- Wallet transactions listing via GET /admin/wallets/transactions.
- Manual adjustments via the backend user credit/debit endpoints.
Loading/error/empty/pagination present.

Not available on the backend (NOT faked — section 18): dedicated pending /
reversed / failed payout queues, a wallet ledger view, and wallet-search by
wallet id. Backend currently exposes transactions + credit/debit only.

12. AUDIT
--------------------------------------------------------------------------------
Backed by real endpoint (frontend/src/app/(admin)/audit-logs/page.tsx):
- Audit log of all admin actions: GET /admin/audit-logs with pagination and an
  entity filter (users, seasons, stages, tournaments, games, notifications,
  settings, cheat-flags). Each entry shows admin, action, entity, entity id,
  changes, IP and timestamp.
This single filterable log covers admin actions, wallet/tournament/enforcement
audits (via the entity filter) rather than separate pages — an honest
representation of the backend's unified audit model. Search/filter and
pagination implemented.
