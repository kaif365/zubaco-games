   tournaments, database-level locking must prevent double-spending.

   payment notifications without crediting wallets twice).

   intervention or orphaned player cohorts.
8. Anti-Cheat Score Verification: The backend must reject scores submitted faster than human biomechanical possibility
   (e.g., moves under 50ms, impossible route completion times, or client-modified score payloads).
9. Regulatory Rigor: 30% TDS withholding calculations on net winnings and GPS geo-fencing for banned states must be

10. High-Concurrency Stability: The system must withstand 1,000+ simultaneous WebSocket connections and 5,000 requests/sec

- Mechanics: A grid of pads illuminates in a specific randomized sequence. The player must wait for the playback to
  finish, then reproduce the sequence in exact chronological order within a countdown timer.
- Procedural Generation & Math Rules:
  * Sequence length starts at 3 items (Level 1) and scales up to 12 items (Level 10).
  * Flash duration must scale down smoothly (e.g., 600ms per pad at Level 1 -> 250ms per pad at Level 10).
  * Randomizer must not repeat the exact same pad more than twice consecutively to prevent visual ambiguity.
- Edge Cases & Bugs to Test:
  * Rapid tapping before playback completes: Pads must ignore input during the demonstration phase.
  * Multi-touch input: If a player presses two pads simultaneously, system must register only the primary pointer.

- Scoring Formula: `Score = (Level * 100) + (RemainingSeconds * 10) - (Mistakes * 50)`.

SECTION 3: MOBILE APP & NATIVE WEBVIEW BRIDGE SPECIFICATION (zubaco-mobile)
========================================================================================================================
The mobile shell is built with React Native. It embeds each game using `react-native-webview`.

3.1. Standardized Bidirectional Bridge Protocol (`postMessage`):
     All messages between the React Native Shell and Game WebView MUST use the following JSON schema:

     A. Game -> Native Mobile Shell:
     -------------------------------
     1. `{ "type": "GAME_READY", "gameSlug": "maze-navigation", "version": "1.0.0" }`
        - Signals that the web bundle is loaded, assets are decoded, and the game is ready for user input.
     2. `{ "type": "GAME_START", "matchId": "match-8912", "timestamp": 1793309100 }`
        - Tells the native shell that the match clock has officially begun.
     3. `{ "type": "SCORE_UPDATE", "currentScore": 1450, "level": 3, "streak": 5 }`
        - Enables the native UI to mirror the score in real-time if necessary.
     4. `{ "type": "HAPTIC", "style": "light" | "medium" | "heavy" | "success" | "error" }`
        - Native shell triggers physical device vibration via `react-native-haptic-feedback`.
     5. `{ "type": "AUDIO_EVENT", "sfx": "tile_click" | "match_win" | "match_loss" }`
        - Triggers native audio playback if running in low-power webview mode.
     6. `{ "type": "GAME_OVER", "payload": { "finalScore": 4200, "stars": 3, "timeRemaining": 12, "moveHistoryHash": "a9f8e..." } }`
        - Signals match completion. Native shell locks the screen and prepares tournament submission.
     7. `{ "type": "EXIT_LOBBY" }`
        - User requested exit from the game menu back to the main app lobby.

     B. Native Mobile Shell -> Game:
     -------------------------------
     1. `{ "type": "INIT_MATCH", "matchTicket": "jwt-token-xyz", "mode": "online" | "offline", "theme": "dark" }`
        - Injects player credentials, encrypted match ticket, and settings into the web environment.
     2. `{ "type": "AUDIO_SETTING", "muted": true | false, "volume": 0.8 }`
        - Synchronizes player's system-level audio preference into the game.
     3. `{ "type": "FORCE_MATCH_END", "reason": "timeout" | "forfeit" }`
        - Forces the game to freeze and produce its final score.

3.2. Physical Device Edge Case Checklist:
     - Safe Area Insets: Use `react-native-safe-area-context` to ensure dynamic island, status bar, and curved screen
       corners do not occlude game controls.
     - Android Hardware Back Button: Intercept `BackHandler` in `GameScreen.tsx`. Display a modal dialog:
       "Leaving this match will forfeit your tournament entry fee. Are you sure you want to exit? [Resume] [Forfeit]".
     - Orientation Locking: Lock games into strict `PORTRAIT` or `LANDSCAPE` orientation per game metadata.
     - App Backgrounding / Phone Calls: Intercept `AppState.addEventListener('change')`. If app is backgrounded during
       a live cash match, start a 30-second forfeit countdown timer.

SECTION 4: CENTRAL PLATFORM BACKEND DEEP SPECIFICATION (zubaco-platform)
========================================================================================================================

4.1. Authentication & Session Architecture:
     - Primary ID: Indian 10-digit mobile number (+91).
     - SMS Delivery Pipeline: Primary provider (Fast2SMS / Gupshup) with automatic fallback to AWS SNS / Twilio.
     - Rate Limiting: Max 3 OTP requests per 10-minute window per phone number.
     - Token Architecture:
       * Access Token: Short-lived JWT (15-minute expiry) containing `userId`, `role`, and `sessionTicket`.
       * Refresh Token: Long-lived cryptographically random token stored in Redis with 30-day expiry.
       * Refresh Token Rotation: Every refresh request invalidates the old refresh token and issues a new pair.
         If a revoked refresh token is presented, trigger instant "Family Invalidation" (freeze all active sessions).

4.2. Concurrency-Proof Double-Entry Financial Ledger:
     - The platform maintains 5 immutable ledger accounts for every user:
       1. `DEPOSIT_CASH` (Funds added via UPI/Cards - non-withdrawable directly without gameplay).
       2. `BONUS_CASH` (Marketing credits - can only subsidize up to 10% of tournament entry fees).
       3. `WINNING_CASH` (Real cash won from tournaments - 100% withdrawable to UPI/Bank).
       4. `PLATFORM_RAKE` (Company commission revenue account).
       5. `TDS_ESCROW` (Government tax withholding account).
     - Database-Level Locking:
       All wallet deductions MUST execute inside a database transaction with row-level locking:
       `SELECT * FROM user_wallets WHERE user_id = $1 FOR UPDATE;`
     - Test Case "Simultaneous Entry": Send 10 concurrent requests to join a ₹50 tournament with a ₹50 balance.
       Only 1 request must succeed; exactly 9 requests must return `HTTP 402 Insufficient Balance`.

4.3. Payment Gateway Webhooks (Razorpay / Cashfree):
     - Webhook Verification: Every incoming payload must be verified against the provider's HMAC SHA256 signature.
     - Idempotency Table: Every webhook has a unique `event_id`.
       The webhook handler checks `payment_webhook_events` table. If `event_id` already processed, return `HTTP 200 OK`
       immediately without re-crediting the wallet.
     - Instant UPI Payout Engine:
       Withdrawal requests trigger an IMPS / UPI payout API call.
       Status transitions: `REQUESTED` -> `PROCESSING` -> `SUCCESS` | `REVERSED`.
       If the bank returns a timeout or ambiguous state, funds remain locked in `ESCROW` until a webhook resolves the state.

4.4. Indian Legal & Tax Compliance:
     - Section 194BA (30% TDS on Net Winnings):
       Net Winnings = (Total Withdrawals in FY + Closing Balance) - (Total Deposits in FY + Opening Balance).
       TDS is deducted at 30% strictly on positive net winnings before dispatching UPI payouts.
       A digital TDS certificate entry is recorded in the user's tax report tab.
     - Geo-Fencing Compliance:
       Banned states: Assam, Odisha, Telangana, Andhra Pradesh, Nagaland, and Sikkim.
       Validation Stack: Client GPS coordinates verified against reverse-geocoding API + IP address verified against
       MaxMind GeoIP database. If either indicates a banned state, lock real-money contests automatically.

4.5. KYC Identity Pipeline:
     - Mandatory threshold: KYC required before any cash withdrawal.
     - Documents accepted: PAN Card (mandatory for TDS) and Aadhaar / Voter ID (for address verification).
     - Storage Security: KYC images are uploaded directly to private AWS S3 buckets using presigned URLs.
       Images are never publicly accessible; URLs expire within 5 minutes.

SECTION 5: REAL-TIME TOURNAMENT & WEBSOCKET ENGINE SPECIFICATION
========================================================================================================================

5.1. WebSocket Gateway Architecture:
     - Gateway: Built on NestJS WebSocket Gateway (Socket.IO with Redis Adapter for multi-node clustering).
     - Heartbeats: `ping` / `pong` packets exchanged every 5 seconds.
     - Reconnection Grace Period:
       If a player experiences network handover (Wi-Fi to 4G) during a match, the socket is disconnected.
       The server reserves their match slot in Redis for 30 seconds.
       If the player reconnects within 30 seconds presenting their valid `matchTicket`, they resume their active level.
       If 30 seconds expire, the match is marked as `FORFEIT` and their accumulated score is locked.

5.2. Automated 5-Stage Tournament State Machine:
     - Every tournament progresses through strict sequential states:
       `[DRAFT]` -> `[REGISTRATION_OPEN]` -> `[REGISTRATION_CLOSED]` -> 
       `[STAGE_1_LIVE]` -> `[STAGE_1_TALLY]` -> 
       `[STAGE_2_LIVE]` -> `[STAGE_2_TALLY]` -> 
       `[STAGE_3_LIVE]` -> `[STAGE_3_TALLY]` -> 
       `[STAGE_4_LIVE]` -> `[STAGE_4_TALLY]` -> 
       `[STAGE_5_LIVE]` -> `[STAGE_5_TALLY]` -> 
       `[PRIZE_CALCULATION]` -> `[PRIZE_DISTRIBUTED]` -> `[ARCHIVED]`.
     - Automated Cron Engine: BullMQ queues in Redis monitor stage timers with millisecond precision.
     - Stage Tally: At the end of each stage, BullMQ executes the cut-off job:
       1. Calculate score threshold for top `(100 - EliminationPct)%`.
       2. Update database: set `eliminated = true` for low performers.
       3. Broadcast WebSocket event `STAGE_RESULTS` to all connected clients.
       4. Start 60-second rest countdown before next stage.

5.3. Cohort Matchmaking Algorithm:
     - When 2,000 players enter a tournament, they are partitioned into balanced cohorts of 50 to 100 players.
     - Cohorts prevent database hot-spotting on a single leaderboard row.
     - Cohort assignment uses consistent hashing on `userId + tournamentId`.

5.4. Leaderboard Precision (Redis Sorted Sets):
     - Leaderboards use Redis `ZADD` with compound scores:
       `CompoundScore = BaseScore + (TimeBonus / 10000)`.
       This ensures ties in raw score are mathematically broken by the player with the fastest completion time.

SECTION 7: ANTI-CHEAT, HEURISTIC SECURITY & PENETRATION AUDITING
========================================================================================================================
Real-money skill gaming platforms are constant targets for malicious actors. The anti-cheat system must defend against
four distinct attack vectors:

7.1. Vector 1: Client Memory Modification (Game Guardian / Cheat Engine):
     - Threat: Modifying the client JavaScript score variable from 1,000 to 999,999.
     - Defense: The client NEVER submits just a raw score number.
     - The client submits a serialized, encrypted log of move timestamps and board delta hashes.
     - The backend verifies: `FinalScore == CalculateScore(MoveLog)`. If mismatched, score is rejected and user is flagged.

7.2. Vector 2: Bot Clicks & Automation Scripts (Auto-Clickers):
     - Threat: Automated scripts tapping puzzles at 100 clicks per second.
     - Defense: Biomechanical Cadence Analysis.
       Human fingers cannot maintain < 50ms click intervals consistently.
       If the standard deviation of click intervals is < 5ms, the session is classified as an automated bot.

7.3. Vector 3: Network Packet Sniffing & Replay Attacks (Postman / Proxies):
     - Threat: Intercepting a winning score payload and re-sending it for multiple tournament entries.
     - Defense: Single-Use Cryptographic Match Tickets.
       At the start of every match, the backend generates:
       `MatchTicket = HMAC_SHA256(userId + matchId + serverSeed + expiryTimestamp, SERVER_PRIVATE_KEY)`.
       The ticket is valid for exactly ONE score submission within the match duration window. Replaying fails immediately.

7.4. Vector 4: Multiple Device Account Farming:
     - Threat: One syndicate operating 50 accounts on 50 emulator instances to collude in tournaments.
     - Defense: Device Fingerprinting via mobile native hardware IDs. Emulators (Bluestacks, Nox) are detected via
       native build property checks and blocked from entering cash contests.
