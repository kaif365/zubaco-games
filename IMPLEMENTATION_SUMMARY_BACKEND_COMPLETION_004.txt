2. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------
A new authoritative reversal entry point was added to the existing enforcement
plane and the only runtime unban path was rewired through it:

  Admin -> POST /anti-cheat/users/:id/unban   (ServiceIdentityGuard)
    -> AntiCheatService.unbanUser(userId, actor)
         -> EnforcementService.reverse({ userId, reason, reversedBy })   (NEW)
              Redis concurrency lock (idempotent)
              Prisma $transaction: clear is_banned + ban_reason  (authoritative)
              post-commit ACCOUNT_RESTORED event (audit, deduped)
         -> return restored user (existing API contract preserved)

reverse() mirrors enforce() exactly: one transaction, a Redis idempotency lock,
and a deterministic post-commit platform event. The legacy direct is_banned write
in unbanUser was removed; the only is_banned writes that now exist in the
canonical tree both live inside EnforcementService (enforce sets it, reverse
clears it). ServiceIdentity is now also threaded into the unban endpoint (the
actor is recorded as reversedBy), matching the existing ban endpoint.

Result: no live runtime performs a direct is_banned unban write; every unban
flows through the authoritative enforcement layer; audit, ServiceIdentity, and
idempotency are preserved; event publication is added. M4 = RESOLVED (see §19).

--------------------------------------------------------------------------------
12. IDEMPOTENCY VERIFICATION
--------------------------------------------------------------------------------
  Layer 1 — Concurrency lock: SETNX acheat:reverse:<userId> rejects a concurrent
            in-flight reversal for the same user (returns alreadyReversed),
            mirroring enforce()'s acheat:enforce lock.
  Layer 2 — Naturally-idempotent transition: clearing an already-clear ban is a
            DB no-op; the event is published only on a genuine banned->not-banned
            transition, so a repeat unban neither errors nor double-audits.
  Layer 3 — Event dedup: ACCOUNT_RESTORED uses a deterministic id, so retries of
            the same reversal never duplicate the audit/webhook fan-out (same
            model as enforce()).
  Note:     the lock is released post-operation (finally) — unlike enforce()'s
            24h hold — specifically so a legitimate later re-ban/un-ban cycle is
            never permanently blocked; idempotency is still fully preserved by
            layers 2 and 3.
