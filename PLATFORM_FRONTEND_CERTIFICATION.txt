1. EXECUTIVE SUMMARY
================================================================================
The "platform frontend" is delivered as TWO applications:

  (A) zubaco-mobile - the React Native PLAYER app. This is the real, intended
      consumer product (the web lobby is explicitly a disposable dev tool, and no
      production web frontend exists yet).

  (B) zubaco-admin-panel/frontend - the Next.js internal ADMIN console.

Headline findings:

  * ADMIN CONSOLE (B): SUBSTANTIALLY COMPLETE (~72%). Authentication, Games,
    Users, Tournaments and Stages are fully wired to the real admin backend with
    forms, validation (zod + react-hook-form), pagination, loading/empty states,
    a 401 interceptor and an AuthGuard. Dashboard and Flagged/anti-cheat are
    functional UIs but backed by MOCK data (TODO: real API). Analytics,
    Notifications, Seasons and Wallets are PARTIAL. Leaderboard admin and a User
    detail page are NOT IMPLEMENTED. 10 unit tests exist. Dark mode + responsive
    are complete. One security item: dummy admin credentials are hardcoded in
    config.

  * PLAYER APP (A): EARLY / DEMO STAGE (~38%). The shell is real and polished -
    navigation, dark theme, OTP auth (send/verify), AuthContext with secure
    Keychain token storage, offline banner, deep-linking, a secure game WebView
    launcher, and a well-defined REST client exposing 27 endpoints. HOWEVER most
    feature screens render HARDCODED / PLACEHOLDER data: Wallet balance and
    transactions, Notifications, Referral, Free Play, and Settings are all mock;
    Tournament and Leaderboard screens are empty skeletons. Only 5 of the 27
    defined API endpoints are actually called. The game launcher passes STUB
    session token values ('pending' / ''), so real play sessions are not yet
    established. Google Sign-In and Onboarding are unimplemented stubs. There are
    0 tests.

  * REAL-TIME: NEITHER app uses WebSockets/socket.io/SSE. All data flow is REST
    (React Query in admin; fetch in mobile). Mobile "live" delivery is intended
    via push notifications (react-native-push-notification) but no wiring exists.

Bottom line: the ADMIN panel is close to production for its wired modules; the
PLAYER app is a convincing UI shell whose commerce-critical surfaces (wallet,
tournaments, leaderboards, notifications, referrals, real game sessions) are not
yet connected to the backend that already exposes the endpoints for them.

2. FRONTEND ARCHITECTURE
================================================================================
-------------------------------------------------------------
A) zubaco-mobile (React Native 0.76, React 18.3)
-------------------------------------------------------------
Stack: React Navigation 7 (native-stack + bottom-tabs), @tanstack/react-query 5,
zustand 5 (declared, minimally used), react-native-webview, biometrics,
device-info, push-notification, google-signin, AsyncStorage + Keychain.
Structure (src/, 25 TS/TSX files total):
  screens/auth   : SplashScreen, OnboardingScreen, LoginScreen, OtpScreen
  screens/main   : Home, FreePlay, Tournament, Leaderboard, Wallet, Profile,
                   Settings, Notifications, Referral, Support
  screens/game   : GameScreen (WebView launcher)
  services       : api.ts (REST client, 27 endpoints), secureStorage (Keychain),
                   biometric, analytics (Firebase - stub/console), crashReporting
                   (Sentry - never initialized)
  contexts       : AuthContext (auth state + token lifecycle), OfflineContext
  navigation     : RootNavigator (auth vs app vs loading), MainTabs (5 tabs)
  components      : AppUpdateModal (force-update; not mounted in App.tsx)
State: AuthContext (global auth), React Query (server cache), local useState for
UI. Token in Keychain. Base URL localhost:3000/api/v1 (dev) / api.zubaco.com (prod).

-------------------------------------------------------------
B) zubaco-admin-panel/frontend (Next.js App Router, TypeScript, Tailwind)
-------------------------------------------------------------
Stack: Next.js (app/ router), React Query, Tailwind CSS, zod + react-hook-form,
custom fetch client. Structure (src/, 226 TS/TSX files, 10 test files):
  app/            : login/, (admin)/ route group with dashboard, games, games/[id],
                   users, tournaments, tournaments/[id], stages, stages/[id],
                   flagged, analytics, notifications, seasons, wallets; root page
                   redirects to /games.
  features/       : auth, dashboard, games, users, tournaments, stages, flagged
                   (each: components/ + hooks/)
  lib/api         : client.ts (fetch wrapper, Bearer from cookie, 401 handler,
                   ngrok header), http.ts (get/post/put/patch/del), endpoints/*
  services/       : auth + thin service layer
  providers/      : React Query provider, auth
  components/layout: AdminLayout, AuthGuard, sidebar/nav
  config/         : routes, query-keys, auth (DUMMY CREDS), game-registry,
                   pagination, navigation
  mocks/          : dashboard.ts, flagged.ts (USED); games.ts, users.ts (dead)
  __tests__/      : components, hooks, services, utils (10 tests)
State: React Query (server), Context (auth user), cookie (token), localStorage
(user + sidebar). Env: NEXT_PUBLIC_API_BASE_URL.

  - No list virtualization concerns yet (lists are tiny mock arrays).
  - Neither app ships real-time transport, so no socket back-pressure concerns.

12. SECURITY FINDINGS
================================================================================
ADMIN (B):
  [HIGH]   Dummy admin credentials hardcoded in src/config/auth.ts
           (admin@ZUBACO.com / Admin@123). Must be removed before production.
  [GOOD]   401 interceptor clears state + redirects; token in cookie; AuthGuard on
           the (admin) route group; credentials:include for cookie transport.
  [NOTE]   ngrok-skip-browser-warning header auto-added when base URL contains
           "ngrok" - fine for dev, ensure prod base URL is a real domain.
  [NOTE]   Mocked Dashboard/Flagged means moderation actions are not persisted /
           auditable yet - a control-integrity gap for anti-cheat governance.
PLAYER APP (A):
  [GOOD]   Tokens stored in Keychain (secureStorage), not AsyncStorage; Bearer
           auth; WebView origin allowlist (game.zubaco.com/localhost) + message
           validation; forced-update modal available.
  [MED]    Game session token passed to the WebView is a stub ('') - once real,
           ensure short-lived, scoped tokens and that they are not logged.
  [MED]    api.logout / auth restore use silent `catch {}` - failures are swallowed;
           no session-expiry/auto-logout on token invalidation.
  [LOW]    crashReporting (Sentry) never initialized -> no production error
           visibility; analytics is a console stub -> no telemetry.
