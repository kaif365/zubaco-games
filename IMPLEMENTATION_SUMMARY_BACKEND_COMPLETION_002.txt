1. OBJECTIVE
--------------------------------------------------------------------------------
Resolve backend implementation item M2: the tournament engine correctly computes
reward eligibility but no live backend runtime credited the winners.
WalletService.creditPrize() existed but was dormant (zero callers). Complete the
authoritative prize payout runtime so eligible winners are credited exactly once,
without redesigning the tournament or wallet architecture.


--------------------------------------------------------------------------------
2. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------
A single authoritative prize payout runtime was added and wired to the existing
pipelines:

  Season COMPLETED (orchestrator.advanceStage)
    -> resolveRewardEligibility(seasonId)          (authoritative winner list)
    -> RewardPayoutService.distributeRewards(...)   (NEW)
         per winner -> WalletService.creditPrize()  (now LIVE)
                       -> WalletLedgerService.post(TOURNAMENT_PAYOUT)
                          (idempotent: ledger_key = prize:<seasonId>:<userId>)
         per credit  -> publish WALLET_CREDITED
                       -> in-app notification (existing subscriber)
                       -> outbound webhook (existing subscriber)

Eligibility (banned/disqualified/incomplete excluded) is owned by the existing
TournamentOrchestrator; the new RewardPayoutService only performs the payout and
takes the pre-resolved winners as input, so it is a one-way dependency (no
circular DI). A per-season Redis lock prevents concurrent double distribution,
and the wallet ledger's per-season+user idempotency key guarantees no winner is
ever paid twice. A manual retry path was added as an RBAC-gated, immutably
audited admin action (DISTRIBUTE_REWARDS).

Result: creditPrize() now has a LIVE caller; TOURNAMENT_PAYOUT is reachable;
banned/disqualified players cannot be paid; duplicate payouts are impossible; the
wallet ledger remains the only balance writer. M2 = RESOLVED (see §20).

7. REWARD FLOW — AFTER
--------------------------------------------------------------------------------
  advanceStage (final stage) -> season status = COMPLETED
        -> publish TOURNAMENT_COMPLETED
        -> resolveRewardEligibility(seasonId)        (banned/DQ/incomplete excluded)
        -> RewardPayoutService.distributeRewards(seasonId, winners)
              [per-season Redis lock]
              -> for each eligible winner with prize > 0 and not banned:
                   WalletService.creditPrize(userId, amount, seasonId)
                     -> WalletLedgerService.post(TOURNAMENT_PAYOUT)
                        (ledger_key = prize:<seasonId>:<userId>, at-most-once)
                   if newly applied -> publish WALLET_CREDITED
                                         -> in-app notification + webhook

  Manual retry (idempotent): admin DISTRIBUTE_REWARDS -> same resolve + distribute.


--------------------------------------------------------------------------------
8. RUNTIME TRIGGER ADDED
--------------------------------------------------------------------------------
  Primary (automatic): TournamentOrchestrator.advanceStage, on the season-
      completion branch, immediately after TOURNAMENT_COMPLETED. This is the
      authoritative completion point, so payout fires exactly when the tournament
      ends. Best-effort (try/catch) so a payout error cannot roll back a
      committed completion.
  Secondary (manual retry): AdminAction.DISTRIBUTE_REWARDS through the existing
      admin control plane — RBAC-gated (FINANCE / SUPER_ADMIN), idempotent
      (requestId), and written to the immutable audit trail. Used if the
      automatic run was interrupted; safe because payout is idempotent.
  No new HTTP endpoint, cron, or queue was introduced (none required — the
      existing admin control-plane endpoint carries the manual action).

10. LEDGER VERIFICATION
--------------------------------------------------------------------------------
  - WalletLedgerService remains the SOLE balance writer. The new service only

  - ledger.post enforces amount > 0 (zero/!positive prizes are skipped upstream).


--------------------------------------------------------------------------------
11. IDEMPOTENCY VERIFICATION
--------------------------------------------------------------------------------
  Layer 1 — Per-season lock: tourn:reward:payout:<seasonId> (setnx + 1h TTL,
            released in finally) prevents two distributions (e.g. automatic +
            admin retry) running concurrently for the same season.
  Layer 2 — Ledger idempotency (authoritative money guarantee): creditPrize uses
            ledger_key = prize:<seasonId>:<userId>, protected by BOTH a Redis
            per-key lock AND a UNIQUE ledger_key index. A second attempt returns
            applied=false / duplicate=true and moves no money.
  Layer 3 — Apply-gated side effects: WALLET_CREDITED is published only when
            res.applied is true, and with a deterministic event id
            (wallet.credited:prize:<seasonId>:<seasonEntryId>) that the event bus
            de-duplicates — so a winner is notified at most once even across
            re-runs.
  Result:   "Already-paid users are never paid twice" holds even under concurrent
            triggers, retries, and re-resolution.
