Approach (honest, no shortcuts):
  • The REAL production service classes are instantiated directly and wired into
    a single shared object graph (test/integration/db/service-graph.ts) backed by
    ONE real PrismaService (bound to the zubaco_test database) and ONE real

  • The ONLY stubbed seam is the outbound SMS provider (SmsService.send) — a true
    external HTTP boundary. Even then the OTP itself still flows through the real
    generate → bcrypt-hash → persist → verify pipeline (the code is recovered from
    the captured SMS text and verified end-to-end).
  • Firebase push (FCM) is inert because no FCM_SERVER_KEY is configured, exactly
    as in a test environment; the push call short-circuits in production code.
  • The webhook/event outboxes only ENQUEUE to Redis (their cron drainers are not
    scheduled when services are instantiated directly), which is the correct,
    honest boundary for these tests.

3. FILES MODIFIED
--------------------------------------------------------------------------------
  • jest.integration.config.js
      Added a moduleNameMapper entry mapping `^uuid$` to a CommonJS interop shim.
      REASON: `uuid` v14 is pure ESM ("type":"module"). Node 24 can require() it
      at runtime (production works), but Jest's module runtime cannot, so importing
      any service that uses uuid (e.g. TokenService) threw "Unexpected token
      'export'". This is a Jest-runtime ESM-interop fix ONLY; it does not touch
      production code. The shim returns REAL RFC-4122 UUIDs via crypto.randomUUID —
      it is NOT a mock of business behaviour.

  (No production/source files were modified.)

DEADLOCK NOTE (honest): a classic two-transaction deadlock is not provoked here.

ledger_key constraint, so a deterministic cross-lock deadlock cannot be forced.
This is documented rather than faked. Postgres' own deadlock detector remains the
authoritative safeguard for any future multi-row lock ordering.

19. REMAINING DB INTEGRATION GAPS (honest)
--------------------------------------------------------------------------------
  1. Leaderboard concurrency: LeaderboardService.updateScore uses a non-atomic
     read-then-write ("only if higher") over Redis. Under TRUE concurrency the
     highest value is not guaranteed to win (a lower late writer can overwrite).
     The test asserts only the real guarantee (a single consistent submitted value)
     and documents this. RECOMMENDATION: switch to an atomic `ZADD GT` (Redis 6.2+)
     or a Lua script. NOT fixed here (production code is out of scope for T4-A).
  2. Event bus & Admin audit have NO Postgres persistence by design (Redis-backed);
     "DB integration" is therefore not applicable to them and is not faked (§12,§14).
  3. Full multi-stage tournament progression (orchestrator.advanceStage across
     several stages with elimination pools + bucketing) is covered at the
     registration/entry and reward-payout boundaries here; deep multi-stage
     elimination simulation is a candidate for a dedicated scenario suite (see §20).
  4. Deadlock provocation is not deterministically testable given the current
     locking model (§15); relies on Postgres' deadlock detector.
  5. Withdrawal/payout settlement lifecycle (createPendingWithdrawal → settle/
     reverse) and OAuth/Razorpay external-provider paths are external-boundary
     heavy and were not in the T4-A section list; recommended for a later phase.
