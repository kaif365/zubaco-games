2. EXISTING HTTP COVERAGE AUDIT (STEP 1 — before writing any test)
--------------------------------------------------------------------------------
Audited the booted application surface directly from source:

 * Bootstrap (src/main.ts): global prefix `api/v1`; helmet(); express json +
   urlencoded (1mb); global ValidationPipe({ whitelist:true,
   forbidNonWhitelisted:true, transform:true,
   transformOptions:{ enableImplicitConversion:true } }); CORS. NO Swagger.

 * app.module.ts: ThrottlerModule.forRoot([{ ttl:60000, limit:100 }]) is
   imported, but NO APP_GUARD / APP_FILTER / APP_INTERCEPTOR is registered
   anywhere. CONSEQUENCE: `@Throttle()` decorators are INERT (no global
   ThrottlerGuard) — there is no HTTP 429 path to test. There is likewise no
   global exception filter or interceptor, so responses use the DEFAULT Nest
   exception shape `{ statusCode, message, error }` (asserted in Section K).

 * Authentication: JWT (JwtStrategy sets req.user = { userId }). OTP send/verify
   is app-level; OtpService enforces a per-phone send rate-limit in code
   (independent of the inert Throttler).

 * Service-to-service surfaces (anti-cheat controller, admin control plane) are
   protected by ServiceIdentityGuard — HMAC-SHA256 over a canonical string
   (serviceId, METHOD, originalUrl, timestamp, nonce, sha256(body)), with nonce
   replay protection in Redis. These are NOT JWT-protected.

 * ScheduleModule.forRoot() is active — cron drainers run inside the booted app,
   so the runner uses --forceExit to terminate cleanly after the suite.

 * config/index.ts throws only for the JWT secrets (provided by the E2E env
   bootstrap). payment-gateway.service reads RAZORPAY_* with `|| ''`, so it does
   not throw at construction under test (money movement remains external).

BEFORE T4-B there were NO booted-application HTTP tests. Coverage existed at the
unit level (T1) and the service+DB / Redis integration level (T2, T4-A), but the
controller/guard/pipe/transport layer had never been exercised over real HTTP.
T4-B closes that gap.

20. REMAINING HTTP GAPS (complete honesty — what is NOT covered over HTTP, & why)
--------------------------------------------------------------------------------
 1. OAuth login (Google / Apple): the Apple strategy imports jwks-rsa -> jose,
    which are pure-ESM and cannot be parsed by the Jest (CJS/ts-jest) runtime;
    they are mapped to a no-op stub so the app can boot. These endpoints verify
    tokens against EXTERNAL identity providers and cannot be exercised over HTTP
    without a live Google/Apple IdP or a heavy forged-JWKS mock. The strategy
    code is UNCHANGED. Not covered over HTTP by design.

 2. Money movement (Razorpay): deposit order creation + settlement webhook and
    the OTP-gated withdrawal PAYOUT require a live Razorpay account/gateway. The
    DTO/validation guards on these routes ARE tested over HTTP (Section F); the
    authoritative ledger behaviour (idempotent credit/debit, balance math,
    double-settlement protection) is proven at the service+DB level in T4-A.

 3. Outbound delivery (Email / Firebase push / SMS send): external providers.
    SMS is captured via the stub to complete the OTP flow; actual email/push/SMS
    DELIVERY is not asserted (nothing to observe without the provider).

 4. GeoFencingGuard (LATENT PRODUCTION BEHAVIOUR — documented, not "fixed"):
    the guard reads `req.user?.id || req.user?.sub`, but JwtStrategy sets
    `req.user = { userId }`. For JWT-authenticated requests neither field is
    present, so the guard never blocks. This is honest observed behaviour; fixing
    it would be a production change, which is OUT OF SCOPE for T4-B (no source
    edits). Flagged here for a follow-up phase.

 5. Automatic cheat DETECTION over pure HTTP: detection runs inside the
    authoritative completion pipeline on the SERVER-derived score, so a client
    cannot deterministically drive a specific flag by inflating a score over
    HTTP. The detection logic is proven deterministically at the service+DB level
    in T4-A; the ENFORCEMENT consequences (ban + leaderboard-score removal) ARE
    proven over HTTP via the admin control plane (Section J and journey J3).

 6. HTTP 429 / global rate limiting: ThrottlerModule is imported but no global
    ThrottlerGuard (APP_GUARD) is registered, so `@Throttle()` is inert and there
    is no 429 path to test. The app-level OTP send rate-limit (enforced in
    OtpService, returning 400) IS covered in Section A.
