9. REMAINING BACKEND IMPLEMENTATION ITEMS
--------------------------------------------------------------------------------
  1. [LOW] Deposit-ORDER idempotency is opt-in (M7 residual).
     Current code: PaymentGatewayService.createDepositOrder dedupes via a Redis
     map ONLY when the client sends an `Idempotency-Key` header; the header is
     optional (wallet.controller.ts). A header-less retry calls createRazorpayOrder
     again and creates an additional Razorpay ORDER. Impact is benign: each order
     is a distinct unpaid intent with its own idempotent PENDING row; only the
     order the user actually pays is credited (ledger.settleDeposit is per-order
     idempotent), and unpaid duplicates are auto-cancelled by WalletCleanupService.
     No double-charge and no double-credit are possible. Closing it fully is a
     backend contract change: require `Idempotency-Key` on POST deposit/create-order
     (or derive a server-side dedup key) so header-less retries cannot create a
     second order.

  No money-safety, ban-bypass, dormant, legacy, duplicate-writer or dead-code
  items remain.

11. MONEY FLOW VERIFICATION
--------------------------------------------------------------------------------
  WalletLedgerService is the SOLE writer of wallet balances. Every credit/debit
  passes through a Redis lock + UNIQUE ledger_key + FOR UPDATE row lock + P2002
  collapse, with an immutable _ledger audit block. Verified keys: prize:<season>:
  <user>, entryfee:<season>:<user>, referral:<ref>:<user>, deposit:<order>,
  deposit:pending:<order>, withdrawal:<uuid>. No balance mutation exists outside
  the ledger (deposit() removed in M9; deposit lifecycle moved into the ledger in
  M5). Balance moves only on deposit settlement (credit) and withdrawal create/
  fail (debit/refund); PENDING/FAILED/CANCELLED deposits move no balance.

14. DEPOSIT FLOW VERIFICATION
--------------------------------------------------------------------------------
  PENDING  -> ledger.createPendingDeposit (idempotent per order id; audited).
  COMPLETED-> ledger.settleDeposit (atomic PENDING->COMPLETED claim + credit;
              verify/webhook race cannot double-credit) -> WALLET_CREDITED.
  FAILED   -> ledger.failDeposit (atomic claim; repeated webhook no-op) ->
              DEPOSIT_FAILED.
  CANCELLED-> ledger.cancelDeposit (atomic claim; loses cleanly to late settle)
              -> DEPOSIT_CANCELLED.
  Order create: idempotent via Idempotency-Key (Redis map + setnx). RESIDUAL:
  header-less retries can still create an extra benign order (Section 9 item 1).


--------------------------------------------------------------------------------
15. WITHDRAWAL FLOW VERIFICATION
--------------------------------------------------------------------------------
  requestWithdrawal -> ledger.createPendingWithdrawal (KYC + balance checked in
  the row-locked tx; gross debited; net on the WITHDRAWAL row; TDS row). @Cron
  worker (per-tx Redis lock, MIN_AGE 5s) -> processWithdrawal ->
  createRazorpayXPayout(reference_id = transactionId, X-Payout-Idempotency =
  transactionId) -> completeWithdrawal (settle) | failWithdrawal (refund).
  Crash-retry re-sends the same idempotency key -> RazorpayX returns the existing
  payout (no duplicate external transfer). Internal ledger at-most-once. No gap.
