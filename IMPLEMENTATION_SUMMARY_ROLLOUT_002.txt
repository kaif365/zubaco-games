--------------------------------------------------------------------------------
1. OBJECTIVE
--------------------------------------------------------------------------------
Make EVERY game-completion path execute the existing authoritative pipeline
instead of a divergent legacy path. Before this phase only ONE engine
(game-session) ran GAME-001 lifecycle + GAME-002 verification; the free-play and
tournament submit paths bypassed both and re-implemented scoring inline. This
phase routes all three completion engines through a single shared authoritative
completion path:

   Lifecycle -> Verification -> Score validation -> Anti-cheat detection
   -> Tournament progression (where applicable) -> Wallet eligibility
   (where applicable, downstream) -> Event publication.

Only existing foundations were integrated. No system was redesigned. No wallet,
tournament, admin, event, RNG, auth, scoring, or infrastructure architecture was
modified.

  A) POST /api/v1/game-session/{id}/submit  (GameSessionService.submitResult)

       + anti-cheat + webhook.  (NO event-bus publication.)

  B) POST /api/v1/free-play/submit          (FreePlayService.submitResult)
       BYPASS: ScoringService.score() directly, duplicated board-tamper check,

       NO lifecycle guard. NO verification pipeline. NO event-bus publication.

  C) POST /api/v1/tournament/submit         (TournamentService.submitTournamentResult)

       NO lifecycle guard. NO verification pipeline. NO event-bus publication.

Result: two of the three live completion paths were NOT authoritative, with

none of the three reached the event bus on completion.

--------------------------------------------------------------------------------
6. RUNTIME EXECUTION PATHS AFTER
--------------------------------------------------------------------------------
All three engines now converge on ONE authoritative routine:

  A) POST /api/v1/game-session/{id}/submit
       GameSessionService.submitResult (input guards)
         -> SessionCompletionService.complete()

  B) POST /api/v1/free-play/submit
       FreePlayService.submitResult
         -> SessionCompletionService.complete()
         -> then stars / level unlock / progress / XP (free-play domain only)

  C) POST /api/v1/tournament/submit
       TournamentService.submitTournamentResult
         -> SessionCompletionService.complete()
         -> then stage-entry total_score/total_time_ms/games_played + stage
            completion (tournament progression)

SessionCompletionService.complete() (every path):
   ACTIVE -> RESULT_PROCESSING            (GAME-001 lifecycle guard)
   -> VerificationPipeline.verify         (GAME-002 authoritative score)
   -> RESULT_PROCESSING -> COMPLETED      (GAME-001 lifecycle guard)
   -> persist authoritative result (_verification metadata)
   -> AntiCheatService.analyzeGameResult  (ACHEAT-001 detection)
   -> EventBus.publish GAME_COMPLETED + VERIFICATION_PASSED/FAILED
   -> WebhookService.emitGameResult       (drives downstream leaderboard /
                                           tournament progression / wallet
                                           eligibility on the Base Platform)

Score equivalence: the DefaultGameVerifier re-implements the exact scoring,
shortest-path folding, board-fingerprint tamper check, discrepancy thresholds
and authoritative-score formula that free-play/tournament used inline, so the
migration is score-equivalent (no silent change to scores, stars, or totals).

9. REMAINING LEGACY PATHS
--------------------------------------------------------------------------------
The completion pipeline itself has no remaining legacy bypass. However, the
following remain OUTSIDE the completion hot path (by design / out of scope):

  EliminationService + the tournament cron + Admin Control Plane, not by the

- The "two control planes" money/enforcement concern from full_audit.txt
  (legacy WalletService direct credit/withdraw, anti-cheat.service direct
  is_banned writes) is NOT addressed here — it is a separate rollout phase.

19. KNOWN LIMITATIONS
--------------------------------------------------------------------------------
- Wallet eligibility and orchestrator-driven tournament stage advancement are
  NOT invoked synchronously from the completion call; they remain driven by the
  Base-Platform webhook and the Admin Control Plane. So "completion -> wallet
  credit" and "completion -> stage advance" are eventually-consistent downstream,
  not in-line. (Deliberate: avoids a parallel money path and respects the "do
  not modify wallet/tournament architecture" constraint.)
- No automated test asserts the unified behaviour end-to-end (TEST-001).
- Event consumers for GAME_COMPLETED / VERIFICATION_* are not yet implemented
  (the in-app subscriber ignores these types), so publication is currently
  audit/observability-grade, not yet wired to a downstream action.
- The metadata key rename (_scoring -> _verification) means historical sessions
  retain `_scoring`; any future reader must handle both shapes.
