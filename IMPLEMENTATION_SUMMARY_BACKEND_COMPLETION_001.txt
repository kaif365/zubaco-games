1. OBJECTIVE
--------------------------------------------------------------------------------
Resolve backend implementation item M1: complete the authoritative withdrawal
lifecycle. Before this change the backend debited the wallet and created a
PENDING WITHDRAWAL row, but NO live runtime path executed the RazorpayX payout or
the settlement/reversal. Wire the existing (dormant) payout/settlement methods
into a single live runtime without redesigning the payment architecture or
introducing duplicate payout/settlement/reversal.


--------------------------------------------------------------------------------
2. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------
The dormant payout chain was already fully self-contained:

  processWithdrawal(txId)
    -> createRazorpayXPayout(...)            (RazorpayX disbursement)
    -> on success: ledger.completeWithdrawal -> PAYOUT_SETTLED
    -> on failure: ledger.failWithdrawal    -> PAYOUT_REVERSED (refund)

The ONLY missing piece was a live caller of processWithdrawal(). A single,
minimal authoritative runtime was added: a cron-based disbursement worker
(WithdrawalDisbursementService) that scans PENDING WITHDRAWAL rows and invokes
processWithdrawal() under a per-transaction Redis lock. No payment logic, ledger
logic, API, or schema was changed — the change is purely additive (one new
provider + its module registration).

Result: processWithdrawal() now has a LIVE runtime caller; completeWithdrawal()
and failWithdrawal() are reachable; payout settlement is no longer dormant;
retries remain idempotent. M1 = RESOLVED (see §20).

6. WITHDRAWAL FLOW — BEFORE
--------------------------------------------------------------------------------
  POST /wallet/withdraw          -> initiateWithdrawal (OTP + Redis intent)
  POST /wallet/withdraw/confirm  -> confirmWithdrawal
        -> requestWithdrawal
           -> WalletLedger.createPendingWithdrawal
              -> wallet debited, PENDING WITHDRAWAL row created
                 ** RUNTIME ENDS HERE **

  Dormant (no live caller):
     processWithdrawal(), createRazorpayXPayout(),
     completeWithdrawal(), failWithdrawal()
  Net effect: funds debited, never paid out, never settled, never reversed.


--------------------------------------------------------------------------------
7. WITHDRAWAL FLOW — AFTER
--------------------------------------------------------------------------------
  POST /wallet/withdraw/confirm -> confirmWithdrawal -> requestWithdrawal
        -> WalletLedger.createPendingWithdrawal  (wallet debited, PENDING row)

  [NEW LIVE RUNTIME — every minute]
  WithdrawalDisbursementService.disbursePendingWithdrawals()
        -> find PENDING WITHDRAWAL rows (age > 5s, oldest first, batch 20)
        -> per-row: acquire Redis lock withdrawal:disburse:lock:<txId>
              -> PaymentGatewayService.processWithdrawal(txId)
                    -> createRazorpayXPayout(...)
                    -> SUCCESS: ledger.completeWithdrawal (PENDING->COMPLETED)
                                 -> publish PAYOUT_SETTLED
                    -> FAILURE: ledger.failWithdrawal (PENDING->FAILED + refund)
                                 -> publish PAYOUT_REVERSED
              -> release lock
  Row leaves PENDING on success/failure, so it is never re-picked.


--------------------------------------------------------------------------------
8. RUNTIME TRIGGER ADDED
--------------------------------------------------------------------------------
  Type ............ Scheduler (NestJS @Cron), mirroring existing wallet-cleanup
                    and event/webhook outbox-drain patterns already in the codebase.
  Schedule ........ CronExpression.EVERY_MINUTE.
  Why a worker .... A retrying worker (not an inline call in the HTTP request
                    path) is the minimal authoritative runtime: it keeps payout
                    latency/timeouts off the user request, and naturally retries
                    PENDING rows blocked by transient conditions, while the
                    per-transaction lock guarantees no duplicate payout. No new
                    queue/admin endpoint was introduced (none required).
  Selection ....... type=WITHDRAWAL, status=PENDING, created_at < now-5s,
                    order by created_at asc, take 20.


--------------------------------------------------------------------------------
9. SETTLEMENT FLOW (success)
--------------------------------------------------------------------------------
  createRazorpayXPayout succeeds (payout id + status)
    -> WalletLedgerService.completeWithdrawal(txId, {payoutId, payoutStatus})
         -> $transaction: updateMany WHERE status=PENDING,type=WITHDRAWAL
            SET status=COMPLETED  (claim.count===0 => already settled => no-op)
         -> metadata stamped with payout id/status + _settlement audit
         -> NO balance movement (debit already happened at PENDING creation)
    -> EventBus.publish PAYOUT_SETTLED  (key: payout.settled:<txId>, dedup'd)


--------------------------------------------------------------------------------
10. FAILURE FLOW (reversal)
--------------------------------------------------------------------------------
  createRazorpayXPayout throws
    -> WalletLedgerService.failWithdrawal(txId, error.message)
         -> $transaction: updateMany WHERE status=PENDING,type=WITHDRAWAL
            SET status=FAILED  (claim.count===0 => already reversed => no-op)
         -> row-locked wallet refund: balance += net payout (mirrors legacy refund)
         -> metadata stamped with error + _reversal audit
    -> EventBus.publish PAYOUT_REVERSED  (key: payout.reversed:<txId>, dedup'd)
    -> processWithdrawal rethrows BadRequestException; the worker catches it and
       logs (already refunded). The row is now FAILED and is not re-picked.

  Pre-payout guard failure (e.g. no verified primary bank detail) throws BEFORE
  any payout and does NOT reverse — the row stays PENDING and is retried on a
  later tick once the user's bank detail is available. No money is debited again
  (the debit already happened once at PENDING creation).


--------------------------------------------------------------------------------
11. IDEMPOTENCY VERIFICATION
--------------------------------------------------------------------------------
  Layer 1 — Run lock: withdrawal:disburse:run (setnx + 55s TTL) prevents two
            overlapping cron ticks from draining the same batch concurrently.
  Layer 2 — Per-transaction lock: withdrawal:disburse:lock:<txId> (setnx + 300s
            TTL) ensures only one in-flight payout execution per withdrawal. This
            is the authoritative guard against DUPLICATE PAYOUT EXECUTION.
  Layer 3 — Ledger claim: completeWithdrawal / failWithdrawal flip PENDING ->
            COMPLETED / FAILED via updateMany WHERE status=PENDING. A second
            attempt finds claim.count===0 and is a no-op, so SETTLEMENT and
            REVERSAL each apply at most once.
  Layer 4 — State exit: a settled (COMPLETED) or reversed (FAILED) row no longer
            matches the PENDING selection, so it is never re-picked.
  Events:   PAYOUT_SETTLED / PAYOUT_REVERSED are published with deterministic
            keys (payout.settled:<txId> / payout.reversed:<txId>); the event bus
            de-duplicates by id, so even a re-publish cannot double-emit.

  Residual edge (pre-existing, NOT introduced by this change; left intact per
  "do not redesign payment architecture"): if the process crashes AFTER RazorpayX
  confirms the payout but BEFORE completeWithdrawal commits, the row remains
  PENDING and a later tick would re-attempt the payout. The RazorpayX call uses a
  non-deterministic reference_id, so this narrow crash-window is not de-duplicated
  at the gateway. This is an inherent property of the existing processWithdrawal
  design and is out of scope for the minimal M1 wiring; it is documented here for
  honesty and flagged as a candidate hardening (deterministic payout idempotency
  key) for a future phase.
